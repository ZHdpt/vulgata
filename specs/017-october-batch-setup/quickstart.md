# Validation Guide: Story 18.4 Plan

This is a future validation guide, not a claim of executable Story 18.4 support. No Story 18.4 migration, host, provider or database command was run during this plan correction. Do not use a shared database or copied credentials. Story 18.1's completed baseline is integrated; the corrected Story 18.4 plan still needs deterministic validation, repeat independent review and applicable approvals before implementation or runtime work.

## Prerequisites

1. Two disposable, explicitly owned PostgreSQL databases with distinct target identities and identical fixed October schema/migration set. Register their exact descriptors under opaque IDs in deployment-owned allowlists for both hosts. Keep the ordinary Web/Identity database distinct; database reachability alone is not authorization.
2. One System member and one standalone Repository with valid management authority and differing Global/System/Repository advisory context. Use a real authenticated Administrator/SystemOwner and an unauthorized user through existing Web Identity. Obtain a purpose-bound activation grant from the Web management authorization seam, not a supplied user ID. For each Repository, use an opaque root-binding version with a deployment-owned generator mapping to an explicitly owned prepared directory. Exercise Story 18.1's actual `PreparedSourceApproval`, `PreparedSourceGrantRequest`, `PreparedSourceContextIssuer` and current-authority verifier, not a substitute source identity.
3. Explicit per-process provider configuration with complete Worker/Chat profiles and synthetic protected credentials; no paid endpoint is needed for setup checks.
4. The in-scope minimal `Vulgata.OctoberGenerator` executable and conditional October Web composition using the same [setup/selection contract](contracts/batch-setup-selection.md) and [provider binding](contracts/provider-binding.md). Supply a disposable, explicitly owned generator client certificate and Web trust allowlist for controlled internal API tests; production certificates and access are separate permissions.

## Controlled checks after implementation authority

1. With the permitted Web-authenticated operator, issue exact A/A and B/B activation grants, then prepare each batch through both host compositions. Confirm each selected context value has scope/origin, conflicts remain visible, the standalone Repository has no System value and is allowed only under current `ManagementAccess`, and no pair, FlowGroup, ScanRun completion or raw legacy Knowledge was manufactured. Retry identical setup and then a conflicting same-ID request; only the former may resolve to the committed result.
2. Run the actual minimal generator executable in `prepare` and `select` modes, and start conditional October Web, with exact A/A and B/B grants/selections. Observe the same chosen setup identity in both hosts and no read/write outside the selected database. Start with missing target, missing batch, A/B mismatch and a batch existing only in the other database. Each must fail before downstream October data access, without earlier/latest fallback; `select` performs no migration. Assert a sanitized nonzero generator exit on failure. Change selection only by restart and fresh authorization.
3. Inspect model/migration metadata and ordinary startup against the pre-change boundary. October mappings/history/snapshot must be separate, normal `VulgataDbContext` must not discover October configurations, and ordinary startup must apply zero October migrations. Exercise explicitly enabled October migration only on an authorized disposable target.
4. Supply complete distinct profiles, deliberate shared profile, omitted field and conflicting source values. Binding must follow one declared source/precedence, reject incomplete/conflicting profiles, expose no secret and never silently fail over. Do not make paid calls as part of setup validation.
5. Call all four Web authority routes through their public seam with an authenticated permitted operator, anonymous and denied operators, a trusted generator certificate, no/invalid certificate and a trusted certificate out of target scope. Check exact closed request/result fields, antiforgery on the cookie route, API-shaped 400/401/403/503 ProblemDetails without redirects/HTML, and cancellation/deadline propagation. Exercise a request/CLI-supplied operator ID or connection string, forged/expired/substituted grant, reachable but unlisted database, mismatched host allowlists, denied or revoked operator, invalid System membership, standalone Repository under a non-management principal, Web authorization outage, cancellation before commit, storage failure and uncertain acknowledgement. Check denial before migration/setup and again at protected use after role/membership/allowlist changes. No selectable partial batch may remain; outcomes must be sanitized and must not claim source tools or Knowledge ready.
6. For each selected Repository, verify exactly one source-binding row for `(BatchId, RepositoryId)` with no physical path. Create a current approval record and prove that its batch, Repository, Web Identity subject, `WorkerSourceRead` purpose, approval ID, root version and label match the `PreparedSourceApproval` passed to the real issuer. Verify `Issued` only with a nonnull context; foreign/expired/revoked approval returns `Denied`, authority outage `AuthorityUnavailable`, unavailable root `RootUnavailable`, and cancellation/deadline their distinct status with no context. Construct `PreparedSourceFunctions` from the issued context and verify the exact three closed functions; revoke authority before a call and before disclosure, then assert no payload/continuation, no reactivation after restoration, and caller disposal after calls settle. Reuse 18.1's containment/schema tests instead of cloning them; no Story 13.1 Git-bound substitute qualifies.

## Evidence levels and command shapes

Static inspection of this plan establishes only design intent. Classify new tests/helpers in `tests/Vulgata.Tests/TestInfrastructure/suites.json`; use `pwsh -NoProfile -File eng/test.ps1` for the configured SelfContained suite, with focused `-Filter` as needed. The configured Web build and an explicit `-Suite PostgreSql` run require separate evidence; the runner must create and clean up owned targets. PostgreSQL checks must identify both owned targets and observed schema/isolation results. Story 18.1's passing final verification is prior evidence for its source tools, not for this production approval adapter. Docker, paid provider execution and later Knowledge publication require their own scoped runtime evidence.
