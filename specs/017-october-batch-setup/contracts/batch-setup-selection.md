# Shared October Setup and Selection Contract

This fixes Story 18.4's generator/Web setup, selection and authorization surface. The Web routes below are required API contracts; this document does not redefine Story 18.1's Worker-facing source tools. Both hosts use the same Core policy and Infrastructure setup writer/selector rather than separate persistence rules.

## Programmatic setup request

Caller-controlled inputs: an allowlisted target ID, exact nonempty batch ID, chosen System/Repository identities (System optional for a standalone Repository), selected applicable Global/System/Repository context references, and an opaque prepared-root binding version plus descriptive operator label for each selected Repository. The trusted generator configuration, not the request, maps each exact `(target identity, batch, Repository, binding version)` to a physical prepared directory. A caller-supplied operator subject, connection string, unlisted target or physical source path is never authority. One immutable binding row per `(BatchId, RepositoryId)` is accepted only after exact setup checks; no setup request grants a root, Git revision or Worker tool by itself.

The explicitly enabled authorization-only October Web bootstrap obtains the operator from its existing authenticated Identity principal and checks live `ManagementAccess` (Administrator or SystemOwner backed by `UserManager`). It validates the target ID against deployment-operator-owned configuration, not database reachability. It checks a System member through current System-owner visibility and Repository membership. For a standalone Repository, it requires current `ManagementAccess`, an existing Repository with `SystemId == null`, and no fabricated System/owner. It then issues a short-lived, purpose-bound Data Protection grant containing the server-derived operator subject and exact target/batch/Repository selection; the raw request cannot set the subject in that grant. This is a new setup authorization seam using existing Identity, not a new login or the Story 18.1 source grant.

Authorization-only October Web validates the grant without opening an October target; the headless generator presents it to that Web authorization endpoint. The endpoint validates protection, expiry and scope and rechecks current Identity role, Repository visibility and deployment target allowlist. It returns a sanitized decision and canonical target identity, never credentials. Generator `prepare` resolves the target ID only through its trusted local allowlist, confirms its canonical descriptor agrees with Web and checks connected-database identity read-only before any October migration. The generator does not reuse Web's request-scoped `IUserContext`, accept a CLI user ID as proof, or treat a successful database connection as authorization. Missing/forged/expired/substituted grants or an unreachable authority fail closed.

The shared policy consumes that trusted authorization result, verifies exact target/batch/Repository agreement, root-binding version and context origins, preserves value/scope/origin/conflict, and commits all setup-owned records atomically within the October database. Ordinary authority and batch data have no cross-database foreign key or distributed transaction, so protected use repeats grant/current Identity, Repository and target checks. It returns the exact target/batch identity and a sanitized outcome. Failed validation, cancellation or persistence leaves no selectable partial batch. An uncertain acknowledgement is resolved by exact target/batch lookup and immutable-input comparison, never by a new target or blind duplicate write.

## Callable Web authorization API

All routes are JSON-only, under plural `/api/` resources, use closed request DTOs with validation, accept a `CancellationToken`, and return sanitized JSON or `application/problem+json` ProblemDetails. Explicit authorization-only October Web bootstrap starts with ordinary Identity/Data Protection and deployment target/certificate allowlists and exposes only the first two grant/validation routes below. It registers no October context, selector, migration, selected-data service or source-approval route and never opens an October target. Selected-data October Web starts only after an exact batch exists and may expose all four routes. Default ordinary Web has none of these October routes or services. No caller may submit a subject ID, connection string, physical root, source tool name or provider secret.

### Closed Web startup and generator-certificate seam

`Program` installs deferred composition through `VulgataWebComposition.ConfigureOctoberHost(WebApplicationBuilder builder) -> void`. This entrypoint schedules configuration-dependent registration; it does not resolve the mode when called. During final host construction its container callback resolves `OctoberWebStartupSelector.Resolve(hostContext.Configuration)` exactly once, registers that immutable `OctoberWebStartupSelection` instance, then adds only the services belonging to that mode before the provider is built. After `builder.Build()`, `Program` obtains the same instance with `app.Services.GetRequiredService<OctoberWebStartupSelection>()` for readiness, migration/startup and route gating; it never resolves the mode again. The selector accepts only these exact `October:Web:Mode` values: absent or `ordinary` selects `OctoberWebMode.Ordinary`; `authorization-only` selects `OctoberWebMode.AuthorizationOnly`; `selected-data` selects `OctoberWebMode.SelectedData`. It never infers a mode from environment name, connection availability or route request. Unknown values and mode-incompatible/partial selection fields fail host construction with a sanitized configuration error before migrations or serving, not an ordinary-mode fallback. The instance is startup metadata, not an October data service or authority capability; ordinary mode registers no October operational service, route, context, selector or migration. Ordinary services retain the existing `ConfigureServices(builder)` entrypoint and behavior.

The executable .NET 10 ordering is part of this interface:

1. Keep existing ordinary/shared service registration early and exactly once, including Identity, Data Protection, ordinary contexts and framework catalog. Install `ConfigureOctoberHost(builder)` once before `Build`; it must not call the ordinary composition again. Retire the premature `ConfigureServices(builder, selection)` overload as the mode-selection path. Preserve the existing cookie options, ordinary startup/migrations and ordinary routes.
2. `ConfigureOctoberHost` explicitly selects `DefaultServiceProviderFactory` and registers `builder.Host.ConfigureContainer<IServiceCollection>((hostContext, services) => ...)`. Preserve the default environment-dependent provider validation options (`ValidateScopes` and `ValidateOnBuild` enabled in Development, disabled otherwise); environment controls these framework options only, never October mode. The callback uses final `HostBuilderContext.Configuration` for mode and allowlists, adds the immutable selection singleton, and performs conditional registrations on the supplied collection. It builds no temporary provider and performs no database/network work. A duplicate installation is a configuration error, not a second registration or re-selection.
3. The explicit factory is essential: `builder.Host.ConfigureServices` executes immediately, and `ConfigureContainer` without an explicit factory is invoked before the inner host build. Neither is a substitute for this deferred callback. With the explicit factory, final app-configuration and test-service callbacks run before the container callback, which runs before the provider is built. Keep existing ordinary fixture replacements effective by leaving ordinary registrations early. Use `TryAdd` for the replaceable `IOctoberAuthenticatedCertificateSource` so a controlled source supplied by `ConfigureTestServices` is retained; always use the same concrete production verifier and configuration-derived allowlist. No test code supplies or overrides the mode selection singleton.
4. After build, consume the registered instance for every mode-dependent startup and route decision. Authorization-only retains ordinary Identity/domain startup and adds exactly the two October grant routes. Selected-data must complete live authorization and exact existing-batch binding before exposing its October routes or data capabilities, and must never migrate an October target. Configuration reload cannot change the captured mode/target/batch or allowlists; switching requires restart. No static ambient state, host diagnostic subscription, test-only route or request-controlled selector is introduced.

This ordering follows the .NET 10 implementation: [ConfigureHostBuilder](https://github.com/dotnet/aspnetcore/blob/v10.0.0/src/DefaultBuilder/src/ConfigureHostBuilder.cs) applies immediate service callbacks and distinguishes explicit-factory container callbacks; [HostApplicationBuilder](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/Microsoft.Extensions.Hosting/src/HostApplicationBuilder.cs) applies final configuration/service changes before creating the provider; [DeferredHostBuilder](https://github.com/dotnet/aspnetcore/blob/v10.0.0/src/Mvc/Mvc.Testing/src/DeferredHostBuilder.cs) replays the factory's configuration during host finalization. These source observations justify the design, but the repository's current runtime still requires the production-host test below; source inspection is not a passing execution result.

The acceptance proof uses the actual `WebApplicationFactory<Program>`: supply mode and allowlists only through `ConfigureAppConfiguration`, resolve exactly one startup-selection instance from the built provider, and assert `AuthorizationOnly`, the same concrete verifier with the controlled source, exactly two October routes, API-shaped denials, and no October data registrations/access. In a separate ordinary host assert the ordinary selection and absence of October operational registrations/routes. Supply invalid mode/partial selection through the same callback and assert failure before startup migrations/serving. Preserve the existing focused failing-host evidence as RED; do not replace it with a selector-only unit test, handcrafted host or forced selection singleton. Test changing configuration after build only to prove that captured selection and registered routes remain fixed, never to enable a runtime mode switch.

The only selected-data host selection keys are `October:Web:TargetId` (nonempty opaque allowlisted ID), `October:Web:BatchId` (nonempty Guid) and `October:Web:ActivationGrant` (protected short-lived grant). All three are required in selected-data mode and rejected in ordinary or authorization-only mode. Authorization-only mode needs no target/batch/grant and remains startable before the October target exists. Deployment-owned `October:Web:AllowedTargets` entries carry exact `TargetId` and canonical database identity; selected-data alone additionally needs a protected connection reference for its selected target, resolved inside its Infrastructure adapter. Deployment-owned `October:Web:GeneratorCertificates` entries carry a SHA-256 certificate fingerprint and its explicit nonempty target-ID set. Both explicit October modes require configured, nonempty applicable target and certificate allowlists; duplicate target IDs, certificate identities or contradictory mappings fail startup. An identity not present in those fixed allowlists never authorizes a target. These collections are host configuration, never request body authority. A `WebApplicationFactory<Program>` sets the same keys through `ConfigureAppConfiguration` and reaches the same `Program` branch without a test-only route or startup flag. Its controlled ordinary Identity store may be supplied by existing test composition; neither the bootstrap branch nor its tests need an October connection.

`OctoberGeneratorCertificateAllowlist` is the immutable normalized mapping from exact target ID to allowed certificate SHA-256 fingerprints, built only from `October:Web:GeneratorCertificates`; it has no request-supplied entries. The verifier is registered unchanged for every October internal route in both explicit modes. Production `IOctoberAuthenticatedCertificateSource` reads a client certificate from the authenticated TLS connection/host certificate-auth boundary, validates trust and validity at that boundary, and derives its fingerprint from the certificate bytes; it never accepts an HTTP header, cookie, body field or unauthenticated proxy claim as proof. A reverse proxy may be used only with a separately protected, authenticated certificate-identity hop; it cannot turn an arbitrary forwarded header into this source. SelfContained `WebApplicationFactory` tests may inject a controlled source result and allowlist entries while still invoking the same concrete verifier and route handlers. `Authenticated` requires a nonempty fingerprint; all other source statuses require no fingerprint. Missing, expired, untrusted or malformed certificate is `Unauthenticated`/HTTP `401`; an authenticated identity not allowlisted for the exact requested target is `Forbidden`/HTTP `403`; unavailable trusted certificate authority/configuration is `AuthorityUnavailable`/HTTP `503`; cancellation ends the attempt without authorization. The route separately rejects a body target different from a selected-data host's fixed target, and still validates the operator grant and live authority. A test-injected identity is not evidence of actual TLS, certificate chain, process or PostgreSQL behavior; T020/T029 retain that owned-resource qualification.

The generator proves its own identity with a deployment-owned client certificate validated by the Web TLS boundary against an explicit allowlist and target scope. The certificate is not a user identity; the operator grant is not generator authentication. Missing, expired or untrusted certificate gets `401`, and a valid generator certificate outside the selected target scope gets `403`. The internal API accepts no cookie-only or caller-supplied certificate header substitute. An ingress may terminate TLS only when its authenticated certificate identity is conveyed over a separately protected trusted hop; otherwise Web must validate the client certificate itself. Production certificate provisioning, rotation and access require explicit owned resources.

The version-2 digest covers the exact validated reference selection and trusted semantic advisory snapshot under the canonical encoding below. Web and Core recompute it; Core compares the result to both request and authority before writing. Caller values/provenance are never accepted. It binds advisory content, not source identity or a Git revision. First-commit SelectedAtUtc is writer-owned metadata outside this precommit digest.

Anonymous operator requests get `401`; authenticated users lacking current `ManagementAccess` or permitted Repository visibility get `403`. Invalid closed DTOs or missing antiforgery proof get `400` ValidationProblem/ProblemDetails. Forged, expired, revoked or substituted activation grants and mismatched prepared-source approval tuples get `403` with only a stable sanitized reason code; no token, path, subject details or record existence leaks. An unavailable Identity/October authority or failed internal Web dependency gets `503` ProblemDetails with `authority_unavailable`, never a cached allow. No `/api/` route redirects to login or re-executes an HTML error page. The generator maps exact current verification to Story 18.1 `Current`, a definite `403` to `Revoked`, and `503`, transport failure or indeterminate response to `Unavailable`; issuance then follows Story 18.1's existing closed statuses.

Each handler and generator client forwards the request cancellation token through live authority and selected-database checks. The generator sets a bounded HTTP deadline no longer than the remaining source-grant deadline; cancellation/timeout stops the current attempt and no cached approval is reused. Operator startup grants and source approvals have explicit short expiries; a fresh activation grant is needed on every generator restart. Approval verification is repeated at issuance and Story 18.1's disclosure checkpoints, including after role, membership, target or root-binding changes. A later restored approval requires fresh issuance, never resurrection of a closed context.

## Process startup selection

The in-scope `src/dotnet/Vulgata.OctoberGenerator` console host has explicit `prepare` and `select` modes and no analysis loop. It takes mode, opaque target ID, exact batch ID, protected activation grant and, for `prepare`, the validated setup selection from a declared host configuration source. It never accepts a caller connection string or physical source path. First-batch `prepare` authenticates with the allowlisted client certificate against authorization-only bootstrap Web, validates the operator grant and local target mapping, checks the connected empty target identity read-only, then and only then runs authorized October migrations and atomically calls the shared `PrepareAsync` setup policy. It does not call `BindAsync` before the first batch exists. A failed check leaves the empty target unmigrated and no selectable batch. `select` validates the grant and calls the shared `BindAsync` selector for an existing exact batch, binds the selected setup capability for its process and emits sanitized target/batch/status before exiting; it runs no migration. Missing target, batch or mismatch exits nonzero before downstream October data access. Later stories may extend this host for generation without replacing its selection contract.

The shared callable selector is `IOctoberBatchSelector.BindAsync(OctoberStartupSelection selection, CancellationToken cancellationToken)` where `OctoberStartupSelection` carries validated target ID, exact nonempty batch ID, and the trusted Web authorization result. It returns `OctoberSelectionResult` with a closed `Selected`, `MissingTarget`, `MissingBatch`, `BatchMismatch`, `Denied`, `AuthorityUnavailable`, or `Cancelled` status and a bound October setup-data capability only for `Selected`; no raw connection descriptor/EF context is exposed through the Core-facing result. A missing or mismatched pair cannot resolve a previous/latest batch.

### One callable Core setup policy

The only Core setup policy callers invoke is `Vulgata.Core.DomainServices.OctoberBatchSetupPolicy`. Its public shape, including constructor, request/authority record construction and result, is fixed for test authors and both host compositions:

`IOctoberSetupWriter` is the existing planned Infrastructure persistence port injected into the policy constructor, with one `CommitAsync(OctoberSetupRequest, OctoberAuthorizedSelection, CancellationToken) -> Task<OctoberPrepareResult>` operation; it is not a second setup policy or a caller-facing database selector. A null writer is programmer misuse (`ArgumentNullException`); malformed/foreign field values are sanitized `Denied`. Trusted application composition constructs `OctoberAuthorizedSelection` only from the live Web validation result and deployment target mapping; it is never bound from an HTTP/CLI request body. The policy checks exact nonempty target/batch, Repository set and canonical selection digest equality between request and authority before the writer can open the owned database. The writer owns the one transaction and exact immutable-input comparison on uncertain acknowledgement.

`Created` and `AlreadyIdentical` are the only success statuses: `CommittedBatch` is nonnull, equals the request's exact target/batch/digest and the authority's canonical database identity, and denotes a committed `Selectable` batch with all setup-owned rows in the selected database. `AlreadyIdentical` means an exact immutable retry observed that committed row without overwrite. `Conflict`, `Denied`, `AuthorityUnavailable`, `Cancelled` and `StorageFailure` have `CommittedBatch == null` and confer no bound capability or proof of partial success. Cancellation before commit leaves no selectable batch; cancellation after an acknowledged commit cannot relabel that commit as failure. No raw connection, physical path, token or exception is returned. Generator `prepare` may invoke this policy after live bootstrap validation and authorized empty-target migration without an existing batch; it never calls `BindAsync` first. After a success, a later generator `select` or selected-data Web must independently call `IOctoberBatchSelector.BindAsync` to obtain an existing-batch bound capability. `PrepareAsync` does not issue one.

After the first batch commits, selected-data October Web and generator `select` each require a protected activation grant, exact allowlisted target ID and batch ID. Each validates authorization and its local canonical target mapping before its selected setup lookup. The shared selector binds one fixed connection/factory to that database, verifies the batch exists there and that its setup identity matches, and makes only that selection available to October consumers. Neither selected-data mode migrates an empty target. No latest/previous-batch query, other-database probe, dynamic EF schema, per-request selection or legacy-wiki fallback is permitted. Switching either element requires process restart and fresh authorization.

October Web keeps ordinary Identity/domain database configuration separate from the selected October database. Default ordinary Web startup has no October context registration, model configuration, routes or migration path. Explicit authorization-only bootstrap adds only the two closed grant/validation routes over existing Identity/Data Protection and allowlists; it does not select, migrate or read an October database and exposes no downstream October service. Only generator `prepare`, after live authorization and connected-target identity check, may migrate an explicitly owned empty October target. Protected setup and later selected-data October use repeat live authorization, including after an operator role, Repository membership or target allowlist change. The startup grant is renewed on every generator restart; an unchanged root-binding version needs no separate reapproval merely because the process restarted.

## Trusted advisory context at the policy and writer seam

**Ownership and selection time.** Only the trusted `OctoberAuthorizedSelection` gains `SelectedContext`; caller `OctoberSetupRequest.ContextSelections` remains typed references, never values or provenance. Live Web management authority constructs the semantic snapshot. The existing one Core policy validates it and passes it to the existing one writer; no Core management reader or second policy is introduced. Initialized `ImmutableArray` members contain copied adapter-owned data and immutable records/strings. A null/default payload is denied even when no context was selected; optional constructor defaults preserve compilation only, never allow old inputs through the new validation.

Selection becomes durable on the first atomic setup commit. The writer stamps one UTC `SelectedAtUtc` from its trusted clock in that transaction for all context entries, returns it on `OctoberCommittedBatch`, and preserves it on `AlreadyIdentical`. Success requires a nonnull UTC time; failure has no committed identity/time. This is selection time, not a source timestamp or grant issuance/refresh time. It is writer-owned metadata outside the precommit semantic snapshot/digest, allowing identical retries across fresh grants without fake precommit times or expired-grant handling. The persisted selection consists of that exact snapshot plus its first-commit time.

**Closed payload.** `ManagementAuthorityId` is a nonempty deployment-owned opaque identity for the ordinary management-data authority, never a caller label or connection descriptor. Trusted `Repositories` contains live-validated Repository/System membership and the requested root-binding/label tuple and must exactly match request tuples and authority Repository IDs. The policy copies any mutable request/reference/Repository-ID collections into an immutable call-local view before validation and forwarding, so concurrent caller mutation cannot change the digest-validated writer input. Every Repository has exactly three entries keyed by `(RepositoryId, Scope)`: Global, System and Repository. Duplicates, omissions, extras, default arrays and unknown enums are denied. Every entry carries `AdvisoryNotSourceProof`. Web resolves `October:Web:ManagementAuthorityId` from deployment-owned final host configuration and captures it with the immutable October startup configuration. It is mandatory and nonblank in both explicit October modes; ordinary mode neither requires nor uses it. This stable identifier names the actual ordinary Identity/management-data authority, not a host instance or batch, and must change when that authority changes. Generator trusted configuration supplies `October:ManagementAuthorityId` for its configured Web authority endpoint; it must equal the live validated snapshot identity, never be inferred from a response, request, target ID or colliding record IDs. Comparison is exact ordinal with no alias/case folding; blank or surrounding-whitespace values are invalid. Configuration changes require restart and cannot rebind an existing batch's stored authority.

At most one Global context reference may be selected; it applies to every selected Repository. System references apply only where the live SystemId equals that record ID; Repository references apply only to that Repository. Every requested reference must be live, accessible and consumed. Selected entries have the matching nonempty origin record ID and exact management `Context` value, preserving legitimate null/empty values. Applicable scopes without a chosen reference are `NotSelected` with null origin/value. A standalone Repository's System slot is `NotApplicable` with null origin/value; other slots cannot be NotApplicable. No flattened text, fake System or inferred source fact is accepted.

`Differences` contains exactly the unordered pairs of Selected scopes within each Repository whose values differ by ordinal comparison (null differs from empty). Each pair occurs once with Global < System < Repository; unselected/nonapplicable slots and cross-Repository pairs are excluded. Core recomputes the set and rejects missing, duplicate or invented pairs before the writer runs. This conservatively exposes differing advisory inputs; it neither diagnoses semantic contradiction nor chooses a winning scope. Original values remain separate.

**Canonical digest.** One public pure Core helper, `OctoberSelectionDigest.Compute(OctoberSetupRequest request, OctoberSelectedAdvisoryContext context) -> string`, returns lowercase SHA-256 hex and ignores `request.SelectionDigest` to avoid self-reference. Structurally invalid input throws `ArgumentException`, mapped to sanitized Denied/400 by the policy/API. Web and Core both use this helper. Encode a UTF-8 JSON array with `Utf8JsonWriter` default encoder, no BOM/whitespace: `[2,targetId,batchId,repositories,contextReferences,managementAuthorityId,entries,differences]`. GUIDs are lowercase invariant D strings. Preserve string contents and reject unpaired surrogates. Repositories sort by ordinal GUID text and encode `[repositoryId,systemId-or-null,rootBindingIdentity,operatorLabel]`; trusted tuples must match. References sort by scope then GUID and encode `[scope,recordId]`. Entries sort by Repository GUID then scope and encode `[repositoryId,scope,applicability,originRecordId-or-null,value-or-null,evidenceKind]`. Differences sort by Repository GUID then left/right scope and encode `[repositoryId,leftScope,rightScope]`. Scope order is Global < System < Repository; wire strings are `global|system|repository`, `selected|not-selected|not-applicable`, and `advisory-not-source-proof`. Reject duplicates before sorting. Independently authenticated subject, grant expiry/token and first-commit time are not content-digest fields.

**Live trust and grants.** Initial issuance checks live Identity, target and complete Repository membership, reads selected management records consistently in one bounded ordinary-data read transaction, materializes the snapshot and calculates the digest. The version-2 protected purpose/payload includes that snapshot, exact selection, server-derived subject and expiry. Version-1 grants lacking provenance fail closed and require fresh issuance. Validation accepts only an unexpired protected grant and identical requested references, verifies/recomputes its snapshot digest and repeats live Identity, target, membership, origin-record access and selected-value checks. Changed selected values/applicability since issuance reject as changed selection; validation never recaptures beneath an old digest. No cross-database atomicity is claimed: this snapshot is what Web authorized at successful validation. Before returning any trusted authorization result, Web compares the protected snapshot's ManagementAuthorityId with its captured live deployment identity and denies any mismatch, even if protection keys and all record IDs collide. The authenticated generator client additionally compares the returned identity to its configured expected authority. Neither an unprotected response field nor possession of an old protected grant changes the live authority identity.

Validation success returns the trusted snapshot as `selectedContext` with its existing sanitized authority fields; advisory text is authorized response data, never logs/errors. Generator prepare supplies it to the existing policy/writer. Fresh authenticated issuance after expiry produces the same digest when semantic context is unchanged, because timestamps are excluded. Changed context on a prepare retry conflicts with the existing immutable batch rather than overwriting it. No prior/expired-grant input or renewal API is added.

Existing-batch generator select/selected-data Web still requires a fresh live grant and exact existing target/batch, subject authority, Repository membership, root bindings and context-reference selection. It returns the batch's stored context/digest/time, never replacing it with newly observed management text. A fresh grant's current advisory-content digest is not required to equal the stored historical digest for read-only binding; the stable organizational/root/reference selection must match exactly. Inaccessible/deleted origins or changed authority/membership/target/root/reference selection deny binding. Ordinary text edits alone neither rewrite history nor force an implicit new batch. ## Prepared-source approval and Worker composition

After setup, October-enabled Web holds a short-lived, revocable current source-approval record in the selected October database keyed by opaque `ApprovalIdentity`. It contains the exact batch, Repository, real Identity subject, `WorkerSourceRead` purpose, root-binding version, descriptive label, expiry and current/revoked status, but no raw activation token or physical path. The configured generator resolves the immutable version to its deployment-owned physical directory and verifies that its mapping agrees with the selected row before issuance. A missing, rotated or revoked mapping denies new issuance and closes an existing context on its next mandatory current-authority check; no old version falls back to another root.

Trusted Worker-session composition forms the existing `PreparedSourceApproval(BatchId, RepositoryId, SubjectId, Purpose, ApprovalIdentity, RootBindingIdentity, OperatorLabel)` and `PreparedSourceGrantRequest(Approval, PhysicalRootPath, Limits)`. It constructs `PreparedSourceContextIssuer` with a production `IPreparedSourceCurrentAuthorityVerifier` that rechecks the exact current record and live Web Identity, Repository, target and root-binding authority at issuance and throughout the context. Exact match returns `Current` with the same approval; revoked/changed/expired authority returns `Revoked`; unreachable or indeterminate authority returns `Unavailable`. The activation grant alone is not a cached allow. No model-visible argument chooses any authority field, root or credential.

Only `PreparedSourceIssueStatus.Issued` provides one `IPreparedSourceReadContext`. The trusted Worker-session caller owns its async disposal after all calls settle and lends it to Story 18.1's `PreparedSourceFunctions.Create()`, which exposes exactly `list_prepared_source`, `read_prepared_source` and `search_prepared_source`. Each context is for one Repository and approval; a batch with several Repositories issues separate contexts. Source operations, budgets, relative paths, sanitized outcomes, cancellation, revocation closure and one-use continuation behavior remain Story 18.1's [accepted contract](../../016-contained-source-tools/contracts/prepared-source-tools.md). No context, handle, physical path or continuation is durable. A different physical root requires new explicit authorization and a new batch or separately reviewed rebind design, not an update to the existing immutable setup row.

## Outcomes and failure classes

Report only sanitized target/batch identifiers and one of: missing selection, forged/expired/substituted grant, authorization service unavailable, unauthorized/unlisted target/operator, invalid organizational/context/root-binding selection, batch absent/mismatch, incomplete provider binding, protected-secret compatibility, migration/storage failure, cancelled, or selected. Prepared-source issuance separately preserves Story 18.1's closed issue statuses, including denied, authority unavailable, root unavailable, unsupported platform, cancelled and deadline exceeded; failure has no context. Logs must omit grants, connection credentials, provider keys, raw source, hidden reasoning and physical source paths. `selected` does not mean contained file tools, native CodeGraph, paid provider inference or Knowledge publication are ready.
