# Research: Owned October Batch Setup

All decisions below are Story 18.4 static planning conclusions. The integrated Story 18.1 final verification at `specs/016-contained-source-tools/evidence/final-verification-01.json` qualifies its own contained source capability; no Story 18.4 database, provider, host or production approval adapter was exercised by this planning correction.

## Database and context ownership

**Decision**: Use one explicitly owned PostgreSQL database per batch and one dedicated October EF context with fixed `october` schema, `october.__OctoberMigrationsHistory` history table and its own migration folder/model snapshot. Generator `prepare` is the authorized first-batch exception; after it commits, generator `select` and selected-data October Web bind an exact existing database and batch ID at startup. Authorization-only bootstrap and default ordinary Web do not bind an October target. Ordinary Web retains its normal database/Identity/domain contexts. **Rationale**: O-FR17 and O-AR03 in `docs/bmad/planning-artifacts/october-release-epics.md`; the accepted October proposal's “Isolate October behavior” section selects database-per-batch, not schema-per-batch. `VulgataDbContext.OnModelCreating` sets `vulgata` and scans all configurations in its assembly; `Program.cs` registers and migrates Identity and Vulgata contexts unconditionally. **Alternatives**: schema search path or legacy table reuse would not redirect schema-qualified mappings and would risk ordinary model/migration contamination. An extra assembly is unnecessary if configuration discovery is explicitly filtered and verified.

**Decision**: Treat authorized database provisioning as an operator prerequisite, not a setup-side `CREATE DATABASE` action. A deployment-operator-owned allowlist maps opaque target IDs to exact database connection descriptors in each host; both hosts must agree on canonical target identity. The Web authorization service approves an allowlisted target before either host opens it for October migration/setup. Reachability is never ownership proof. The setup writer creates only its own batch metadata in that target, transactionally; exact target/batch lookup precedes any consumer data access. **Rationale**: Story 18.4 acceptance and `docs/agents/testing.md` require owned resources and reject cross-target fallback. **Alternatives**: request-supplied connection strings, “latest” selection, dynamic switching and partially published setup are excluded by O-FR17.

**Decision**: Add a minimal .NET `Vulgata.OctoberGenerator` executable now, with explicit `prepare` and `select` modes. An explicit authorization-only October Web bootstrap composition starts first with existing ordinary Identity/Data Protection, management Repository/context authority reads and deployment target/certificate allowlists; it exposes only grant issuance/validation and never registers or opens an October context. Generator `prepare` validates the grant through that route, checks the connected owned empty target identity, migrates it and atomically creates the first batch through the shared Core policy. It does not call the selected-data selector before creation. After commit, generator `select` and selected-data October Web use the same Infrastructure selector for an exact existing batch; neither migrates. **Rationale**: Story 18.4/O-FR17 requires an executable two-host startup path, and the approval clarification IA-18.4-BOOTSTRAP-01 found that requiring Web selection before the first grant creates a circular dependency. **Alternatives**: preseeded batch, fake authorization, a test-only stub, a general bootstrap platform or a full analysis host are unnecessary or violate the accepted story boundary.

## Identity, organization and context

**Decision**: Persist a server-derived real operator subject and a validated organizational selection. Explicit authorization-only bootstrap Web authenticates the operator through existing Identity and checks live `ManagementAccess`; its `UserManager`-backed handler proves Administrator/SystemOwner role. It issues a short-lived, purpose-bound protected activation grant scoped to operator, target, batch and Repositories without consulting an October database. The generator presents it to bootstrap Web's authorization endpoint for protection/expiry and live Identity/Repository/target checks before migration/setup; selected-data Web performs later protected-use checks after an existing batch is bound. This uses Web's existing Identity owner; request-scoped `IUserContext` cannot be the headless generator's identity source. For a System member, require current owner-filter visibility and matching membership. For a standalone Repository, require current `ManagementAccess` plus an existing `SystemId == null` Repository; do not pretend it has a System owner. The current `RepositoryAuthorizationVerifier` rejects standalone Repositories and cannot be reused unchanged. The batch database has no cross-database foreign key or atomic transaction with the authority; a stored subject is provenance, not continuing permission. **Rationale**: PRD FR-1.4/FR-2.1–2.4, canonical glossary, O-FR18, `UserContext`, `ManagementAccessRequirement`, `RepositoryManagementCoordinator` and Story 18.4. **Alternative**: accepting a CLI/request user ID, copying role claims or fake Identity rows, or treating a reachable DB as owned would make authority forgeable or stale.

**Decision**: Pin four plural-resource Web POST routes in [the shared contract](contracts/batch-setup-selection.md), with mode-specific availability: authorization-only bootstrap exposes cookie/antiforgery-protected operator grant issuance and generator-only grant validation; selected-data Web may additionally expose source approval creation and exact current-authority verification after binding an existing batch. Internal routes require a separately allowlisted mutual-TLS generator certificate scoped to the target plus the operator grant where applicable. They return closed sanitized results and 400/401/403/503 ProblemDetails without cookie redirects or HTML status-page re-execution. Cancellation/deadline propagates; source verification maps definite denial to Story 18.1 `Revoked` and unavailable/indeterminate authority to `Unavailable`. **Rationale**: Constitution III/V, `src/dotnet/Vulgata.Web/Program.cs` API cookie behavior and existing `/api/` resource conventions require a concrete callable trust boundary; a startup token alone cannot identify a trusted generator or establish live source authority. **Alternatives**: trusting only a CLI/user ID or protected bearer grant permits caller substitution; a handwritten request-signature protocol would add avoidable cryptographic policy. Certificate provisioning and production Web access remain separate authorized resource work.

**Decision**: Retain selected Global, optional System, and Repository advisory context as separate values with scope, originating record and selection time, plus explicit disagreement indicators; do not collapse them into one source-qualified statement. **Rationale**: PRD FR-7.3, Story 18.4/O-FR02 and AD-2. Current `GlobalContext`, `System.Context`, `Repository.Context` provide candidate values, while `IContextCompositionService.ComposeEffectiveContextAsync` returns flattened text and cannot alone retain origins. **Alternative**: reuse flattened text only would lose provenance and silent conflicts.

## Executable advisory provenance and stable selection time

**Decision**: Web's live management-authority adapter supplies one immutable `OctoberSelectedAdvisoryContext` in the trusted `OctoberAuthorizedSelection`, not in caller `OctoberSetupRequest`. The request retains typed references only. The exact records, three applicability slots per Repository, deterministic differing-value pairs, advisory classification and shared v2 digest encoder are fixed in [the setup contract](contracts/batch-setup-selection.md). Core keeps one policy and one writer; it validates and forwards the trusted snapshot without querying management persistence. **Evidence**: the current policy can receive only scope/record IDs and therefore cannot validate or retain values at its public seam (I-18.4-CONTEXT-PROVENANCE-SEAM-01). **Alternatives**: caller-supplied values are forgeable, flattened context loses provenance, and a new Core reader would duplicate Web authority responsibilities.

**Decision**: The writer owns `SelectedAtUtc` at first atomic batch commit and preserves it on exact retry. The precommit grant/digest covers the entire immutable semantic snapshot but excludes grant/commit times; persistence retains snapshot plus committed time. **Rationale**: selection has not become durable before commit. Using grant-issuance time in identity would make unchanged fresh grants conflict; origin UpdatedAt is a management edit time, not selection time. An expired prior grant as provenance input adds unnecessary replay handling. No such input is added; every operation still requires fresh current authority. Grant v2 contains the snapshot and validation compares it against current live selected values; changed same-grant content denies. Fresh issuance of unchanged semantic content preserves its digest.

**Decision**: Read-only binding of an existing batch checks current authority and exact stable organizational/root/context-reference selection, then exposes stored historical context/time. A fresh grant's current advisory values cannot overwrite that history and need not equal it. Prepare of an existing batch instead compares the complete snapshot and returns Conflict on a content change. **Rationale**: FR-003 requires immutable provenance despite later management edits; FR-005 still requires exact batch identity and no fallback. This distinction changes neither source authority nor provider selection and needs independent review and affected task/approval reconciliation. **Continuity correction P-18.4-05**: require exact stored-versus-current ManagementAuthorityId before binding. Web freezes the deployment-owned October:Web:ManagementAuthorityId and compares it to protected v2 provenance at validation; generator pins October:ManagementAuthorityId for its authority endpoint. Record-ID equality alone cannot prove continuity across different management authorities. A different authority with colliding IDs denies; same-authority text edits preserve the accepted historical-read behavior.

## Provider and secret configuration

**Decision**: The provisional implementation route is an explicitly supplied host configuration source per process with complete endpoint/model/credential reference/API type and separate Worker/Chat role profiles. The operator must supply the source and precedence; no `.env` path is inferred or discovered. A shared profile requires an explicit declaration. **Rationale**: O-FR19, PRD FR-3.1–3.4, accepted October proposal's provider section and existing `Program.cs` Data Protection/registrations. **Alternatives**: silent field mixing/auto failover is prohibited. A database configuration route may be substituted only after explicit selection and design reconciliation; encrypted-row copy then requires compatible Data Protection keys, application identity and purpose (`SecretEncryptionService` uses a purpose-specific protector).

**Decision**: Binding checks configuration completeness, not paid provider availability or model quality. Sanitize source identity and failure class in diagnostics; never emit credentials, raw source or a false tool/Knowledge readiness claim. **Rationale**: Constitution V, AD-32 and Story 18.4. **Alternative**: live inference as a setup health check would spend resources and conflate later qualification.

## Integrated Story 18.1 source binding

**Decision**: The selected October database stores one immutable opaque `RootBindingIdentity` version and descriptive `OperatorLabel` per `(BatchId, RepositoryId)`; only trusted generator configuration maps that version to a physical prepared directory. One `PreparedSourceApproval` binds the exact batch, Repository, real Identity `SubjectId`, `WorkerSourceRead` purpose, current `ApprovalIdentity`, root version and label. Trusted composition passes it with the configured `PhysicalRootPath` and bounded `PreparedSourceGrantLimits` in `PreparedSourceGrantRequest` to `PreparedSourceContextIssuer.IssueAsync`. **Rationale**: The completed Story 18.1 [Core contract](../../src/dotnet/Vulgata.Core/DomainServices/PreparedSourceContracts.cs), [issuer](../../src/dotnet/Vulgata.Infrastructure/Source/PreparedSourceContextIssuer.cs) and [accepted contract](../016-contained-source-tools/contracts/prepared-source-tools.md) fix that tuple and give the Worker only `IPreparedSourceReadContext`. A Git revision, Source Snapshot, physical path in October rows or second tool grant would contradict this boundary. **Alternatives**: batch-only or Repository-only binding is insufficient; copying a path/handle/cursor into durable setup would make authority stale or disclose host configuration.

**Decision**: After valid setup, October-enabled Web retains a short-lived, revocable approval record in the selected October database keyed by opaque `ApprovalIdentity`, with tuple/expiry/status but no raw activation token or physical path. The generator-side production `IPreparedSourceCurrentAuthorityVerifier` rechecks Web's record and live Identity/Repository/target decision plus its own immutable deployment mapping for the exact root-binding version at issuance and before each disclosure. A changed/revoked tuple returns `Revoked`; failed/unreachable authority returns `Unavailable`. Startup activation is fresh on every generator start but never substitutes for those live checks. A mapping change requires a different version. **Rationale**: Story 18.1's verifier is mandatory and its read context closes on authority loss; the accepted direct tests use an in-memory verifier but explicitly leave production approval sourcing to later setup. Story 18.4 owns that source. **Alternatives**: an always-current verifier, startup-only token check or cached allow would retain disclosure after revocation; requiring new root approval on every restart despite an unchanged version adds operator friction without replacing live checks.

**Decision**: A future trusted Worker-session caller owns and disposes each issued `IAsyncDisposable` context after all borrowed `PreparedSourceFunctions.Create()` calls settle; Story 18.4 qualifies its direct issuer/approval seam, not Worker dispatch. The three existing functions are exactly `list_prepared_source`, `read_prepared_source` and `search_prepared_source`; Story 18.4 adds no model-visible authority selector. Cancellation, deadline, disposal, revocation and verifier outage retain Story 18.1's closed status, empty-payload and continuation-invalidation behavior. **Rationale**: `PreparedSourceFunctions` borrows a single context; the accepted [source contract](../016-contained-source-tools/contracts/prepared-source-tools.md) and focused tests in `tests/Vulgata.Tests/PreparedSource` already qualify this API directly. **Alternatives**: a durable context/continuation, per-call reissuance or fourth tool would duplicate or broaden 18.1.

## Compatibility and verification

**Decision**: Add conditional October compositions only when explicitly enabled. Default ordinary Web and authorization-only bootstrap register no October mappings/context/migration path; the latter adds only closed authority routes. Generator `prepare` alone may run October migrations after live authorization and connected-target identity verification; selected-data Web and generator `select` require an existing batch and run no migration. Preserve normal Web's existing ordinary migration/role seeding path. Test a freshly created owned empty target through bootstrap-to-first-batch, then two owned PostgreSQL databases with identical October schema and normal startup regression. **Rationale**: O-AR01–04, `Program.cs`, `VulgataDbContext.OnModelCreating`, constitution IV and testing guide. **Alternatives**: SQLite-only, static schema inspection or preseeded batches cannot prove first-batch reachability or PostgreSQL cross-database behavior. Neither controlled tests nor a migration script alone proves Docker/provider/source-tool qualification.
