## Architecture Decisions

### AD-1: One prepared pair execution, one atomic complete job set

`Pass1PairExecution` binds the exact Story 12.2 pair and both accepted Story 12.1 Scan Executions. Start requires their already-persisted nonempty prompt identity, exact `code-logic/file-v2` schema identity, and accepted runtime identities; it never invents or rewrites them. It reconstructs both packages and inserts the pair, every job, and every navigation budget in one PostgreSQL transaction before any claim. Concurrency is stored but excluded from all content/identity ordering. Alternative lazy creation or start-time rebinding is rejected because it exposes partial queue state or breaks replay identity.

### AD-2: Pair-row locking owns shared capacity, active reconfiguration, and canonical claim order

One versioned pair row serializes capacity accounting. Claim first recovers strictly expired leases and releases due nonexhausted Story 12.3 retries, counts current unexpired Running leases across both children, and selects the smallest eligible Pair Selection Ordinal. Its server-only result includes current job/pair versions, lease token/expiry, ordinals, and next durable eligibility; a specific packet source revalidates that claim after revision-bound source hydration. A separate authorized expected-version command changes effective limit 1-4, appends a canonical audit record, preserves existing leases, and affects only later claims. Initial concurrency remains for exact Start replay; effective concurrency remains outside scan/content/display identity. Existing Manifest Ordinal remains Repository-local display order. Alternative independent semaphores/`SKIP LOCKED`, caller-built packets, lease revocation, or changed-Start mutation are rejected because they violate the shared cap, current lease authority, accepted leases, or replay meaning.

### AD-3: One claimed-job executor-owned conversation, not legacy sequential mutation

A Story 12.3-specific claimed packet source builds one v2 packet only after validating the current lease. `PreparedPass1JobExecutor` owns the complete current-job-only provider conversation, strict functions, streaming deadlines, and execution-local accepted-result capture. `PreparedPass1WorkerDispatcher` owns no outer provider-turn loop; it maps only the executor's closed result/failure to the current lease-bound commit path. The production job runner owns durable claim/commit/failure sequencing. Legacy `WorkerAgentDispatcher`, retry decorator, v1 result and Pass 2 prepared-demo seams remain unchanged. Alternative caller-supplied multi-job batches, nested dispatcher/executor conversations, or in-place legacy mutation is rejected because they cannot prove one turn/submission authority or current lease ownership and would silently alter accepted Story 11/12.1 behavior.

### AD-4: Exactly two closed functions with one evidence-access seam

The Agent sees exactly `navigate_code` and `submit_code_logic`, both provider-strict. `navigate_code` remains the sole evidence-access function with eight operation enum values; the server binds all scope identity and composes only current-Document reads, accepted JDT LS/CodeGraph typed operations, Story 12.2 approved inventory, and exact revision-bound source reads. Absence/out-of-scope are indistinguishable. `submit_code_logic` is the sole non-evidence finalization function and delegates only the nested `document` candidate bytes to the full local parser; it cannot read source or other jobs. Alternative free-form final JSON, raw commands, multiple evidence tools, or a submission function that retrieves evidence is rejected because it bypasses capture/local authority or expands disclosure.

### AD-5: Durable attempt/call/evidence/depth budget and receipt proof

Ten provider turns, eight job-wide `navigate_code` attempts, and two submission invocations are separate ceilings. `ToolAttemptCount` is the persisted contiguous reservation high-water shared across retry/restart. Each navigation callback requires a current-lease/version reservation first; every committed reservation remains consumed regardless of receipt/outcome/crash. Receipt commit binds to that ordinal, never increments attempts twice, and releases evidence only after commit. Refusals use the reserved ordinal; marker nine is ensured after reservation eight and repaired before retry/terminal visibility. Submission state remains execution-local. Reset-per-retry or receipt-only attempt counting is rejected because it permits restart bypass.

### AD-6: Full local v2 authority through execution-local submission capture

Only the nested `document` JSON object from `submit_code_logic` can become a candidate. The pinned adapter is proven to discard outer encoded `BinaryData` after parsing to a dictionary, so the invoker requires exactly one key named `document`, requires its value to be an object `JsonElement`, and passes `GetRawText()` directly to `PreparedPass1ResultParser`; dictionary reserialization and typed binding are forbidden. AD-29 may project only a fixed repair code derived from that closed kind. Communication kind is closed to `Rpc|Http`; every classification binding must exactly equal the referenced Story 12.2 ID, fingerprint, kind, strength, rule/provenance, Catalog Rule Identity, and Evidence Locator, and mixed/mismatched kinds reject. A valid candidate is captured atomically in execution-local state and immediately terminates; free-form text is disregarded. A second invalid submission, third attempt, later navigation, unknown/mixed/multiple-submission/post-submission/above-eight response, or turn exhaustion rejects; AD-21/AD-23 permit a completely preflighted at-most-eight all-navigation response and close only the siblings beyond current capacity. The Worker never authors server IDs, ContentMarkdown, Document Sections, search text, Index Entry, Edge IDs, or fingerprints. A manual SDK loop is rejected as unnecessary added ownership while this tested `JsonElement` seam preserves candidate bytes. Alternative provider-schema authority, dictionary reserialization, JSON repair, final-text parsing, detailed validator feedback, or LLM-authored projections is rejected because authority/replay/privacy would diverge.

### AD-14: Explicitly activated single-flight host execution service closes the production call graph

Authenticated Start/eligible exact replay, manual Resume, and concurrency update signal a bounded in-process pair activation. One Windows-host `BackgroundService` deduplicates the pair into one single-flight coordinator, but that coordinator is normatively capacity-filling: it serially obtains durable claims and launches each claim in an independent DI-scoped job runner without awaiting an earlier runner, repeating until the store reports `AtCapacity`, future/ineligible work, or a circuit/terminal state closes dispatch. Runner completion is only a wake-up to reload durable state and fill newly available slots; it never chooses the next job or contributes to identity/order. A 4-to-1 change preserves all four leases and suppresses replacements until durable active count falls below one; a 1-to-4 change wakes Fill and launches up to three more eligible runners while the first may remain blocked. A closed circuit/pause/failure/cancellation stops launches immediately, then already-launched runners drain to closed durable outcomes. `ReconcileAsync` is legal only after the local runner set is empty and a fresh durable claim proves zero active/Pending/future-retry work. PostgreSQL remains the execution authority; the channel and local completion handles contain no File Code Unit authority and cannot choose order/capacity/retry/terminal state. A coordinator that awaits one Worker before making the next claim is explicitly nonconforming. The service does not discover persisted work at startup and stops permanently for that activation after the fifth provider failure, so the accepted manual `继续扫描` boundary remains intact. Alternative sequential claim-to-completion execution, long-running HTTP execution, per-file in-memory queue, startup database sweep, or automatic paused-pair recovery is rejected.
