# DeepSeek V4 current-practice audit for Story 12.3

**Audit date:** 2026-08-25 (Asia/Shanghai)

**Scope:** read-only audit of the Story 12.3 DeepSeek plan, contract, prompt, executor, declaration projection, and focused tests after T084 r16.
**Source policy:** current first-party DeepSeek documentation and privacy policy, repository authorities, pinned package documentation, and current source only. No provider request, source-bearing request, database operation, or system/host change was performed.

## Verdict

T084 r16 is blocked by one confirmed protocol-policy mismatch, not by DeepSeek availability or the host. DeepSeek's current Chat Completions contract defines the default `tool_choice: auto` behavior as allowing a normal message or **one or more** tool calls. The current final wire intentionally omits `tool_choice` and the undocumented `parallel_tool_calls` field, but `PreparedPass1JobExecutor` rejects every assistant response whose `FunctionCount != 1`. T084 r16 observed exactly that legal multiple-call shape and therefore ended as `IllegalFunctionCall/MultipleFunctions` before invoking any call.

The smallest robust correction is not to restore an undocumented request field and not to rely on prompt wording alone. Correct the plan and executor to:

1. tell the model to emit one function call per assistant response and require `submit_code_logic` to be the sole call in its response;
2. defensively accept a bounded batch only when every call is the declared `navigate_code`, the entire batch fits the remaining navigation-attempt budget, and the batch can be preflighted before any invocation;
3. invoke that accepted batch serially in provider order, return one matching tool result per call ID, and preserve the complete assistant `reasoning_content`, content, call array, and tool results on the next request; and
4. continue rejecting unknown, mixed navigation/submission, multiple-submission, post-submission, or over-budget batches before any callback, receipt, candidate validation, or later request.

This changes a Worker Agent tool-execution rule and therefore triggers a corrected plan/definition/TDD review cycle. The user's standing authorization permits that cycle without another approval pause; it does not waive independent review or qualification gates.

The audit also found three latent issues that did **not** cause T084: SSE keep-alive comments do not reset the current outer inactivity timer; 402/422 status handling is imprecise; and the final wire does not explicitly reject thinking-mode sampling fields that DeepSeek silently ignores. These should be corrected in the same bounded transport review before the next source-bearing attempt.

## Evidence for the T084 cause

- [`failure-29.json`](../tdd/failure-29.json) records one source-bearing job, 58 seconds, `IllegalFunctionCall`, subtype `MultipleFunctions`, no provider HTTP error, no timeout, no wire overflow, no submission validation, and no later job.
- The request used the same projected schema hashes that passed the source-free handshake: `navigate_code` `779250FC...A1FDA` and `submit_code_logic` `3CD6F35E...DB20F`.
- [Chat Completions `tool_choice`](https://api-docs.deepseek.com/api/create-chat-completion/) says `auto` is the default when tools are present and can produce one or more tool calls.
- [Thinking Mode tool-call guidance](https://api-docs.deepseek.com/guides/thinking_mode/) iterates every returned tool call and appends one matching tool-result message per call ID.
- The current plan/contract explicitly classify multiple calls as illegal, and [`PreparedPass1JobExecutor.cs`](../../../../src/dotnet/Vulgata.Agents/WorkerExecution/PreparedPass1JobExecutor.cs) terminates when `FunctionCount != 1` even though its later continuity validator already supports an assistant message containing multiple unique call IDs followed by matching tool results.
- The current prompt describes exactly two registered functions but does not state that one assistant response must contain only one call.

No call names, count, IDs, arguments, reasoning, content, response bytes, source, or credential were retained. The exact r16 combination is intentionally unknown. The recommendation therefore does not assume that the returned batch contained any particular function names.

## Classification of findings

### Confirmed mismatch that caused T084

`tool_choice:auto` legally permits multiple calls, while the accepted executor treats `FunctionCount != 1` as an illegal provider response. `AllowConcurrentInvocation=false` serializes callbacks; it does not make the provider's response cardinality one. Removing `parallel_tool_calls:false` was correct because current first-party Chat Completions documentation does not expose that control. The response policy, not the request field, must be corrected.

Prompt-only serial guidance is useful but insufficient. Function descriptions and instructions shape generation; they do not constrain `tool_calls` array cardinality. The executor must remain safe when the model ignores that guidance.

### Latent risks to correct before the next source-bearing run

1. **Keep-alive visibility:** the current five-minute timer observes parsed model updates, not raw SSE progress. A healthy request can receive official keep-alive comments without producing an `AgentResponseUpdate` and be cancelled locally before DeepSeek's ten-minute pre-inference boundary.
2. **Status precision:** source-free 402/422 currently look transient, while they require balance/parameter correction. Production safely pauses as unclassified but should expose the existing non-retryable configuration class instead.
3. **Ignored controls:** thinking-mode sampling fields should be absent and fail closed if they appear. Silently allowing ignored settings makes an intended determinism/control knob ineffective.

These risks did not cause r16: it ended in 58 seconds with a completed streamed response shape, no HTTP error, and no timeout.

### Conservative local policy that should remain

- exact `/beta` endpoint for strict mode and no application endpoint rewrite;
- one shared, hash-bound projected declaration authority and complete local `code-logic/file-v2` validation;
- no `tool_choice`, `parallel_tool_calls`, or `response_format` on the final thinking/tool wire;
- explicit thinking enabled, default-high reasoning effort, `max_tokens:32768`;
- Vulgata's raw/assembled/replay/request byte caps, ten provider turns, two submission invocations, eight navigation attempts, five-minute no-byte inactivity, 25-minute absolute cap, and 30-minute lease relationship;
- zero SDK retries and durable provider recovery as the sole retry authority;
- unknown function rejection, local candidate validation, atomic commit, immutable Document graph, and no payload logging.

### Nonissues

- Provider schema, endpoint, model, credential, network, database, timeout, and host configuration were excluded by T083 plus r16 evidence.
- The provider's 384K output maximum does not require Vulgata to increase its 32,768-token cap.
- Omission of `reasoning_effort` uses the documented default `high`; it is not evidence that thinking was disabled.
- Provider account concurrency is orders of magnitude above Vulgata's 1-4 pair cap.
- `$def`/`$ref` provider support does not require Vulgata to stop using a safer fully inlined, drift-checked projection.
- `user_id` is optional and is not a no-log/no-retention mechanism.

## 2026-08-25 r17 delta audit: mandatory tool protocol

T084 r17 invalidates the remaining assumption that bounded multiple-call handling makes omitted/default `tool_choice:auto` sufficient. The first source-bearing job completed one streamed response with no function call, no HTTP or timeout error, no navigation reservation or receipt, no candidate, and no Document. The executor correctly surfaced `MissingSubmission`, but the request contract allowed exactly that normal-answer branch. The externalized prompt already says that every response must be either a sole submission or an all-navigation batch, so further prompt wording cannot make the protocol deterministic.

The current first-party [Chat Completions contract](https://api-docs.deepseek.com/api/create-chat-completion/) states that `auto` can return a normal message or one or more calls, while `required` requires one or more calls. Current [DeepSeek V4 integration guidance](https://api-docs.deepseek.com/quick_start/agent_integrations/oh_my_pi/) also states that thinking mode does not support `tool_choice`. Two bounded source-free streamed probes against the approved route/model/key confirmed the combination rather than inferring it from prose:

| --- | --- | --- | --- |
| enabled | `required` | HTTP 400 | `invalid_request_error`; no call and no `[DONE]` |

No source, prompt packet, Repository/System/Scan/job identity, tool argument, response content, credential, header, or host path was included in either probe or retained in evidence.

### Revised verdict

For a Worker protocol in which free-form completion can never be authoritative, the smallest robust Chat Completions contract is streamed non-thinking execution with mandatory tool selection. Ordinary requests use exact `tool_choice:"required"`; the r21 delta below supersedes only the terminal request with exact named `submit_code_logic`. Both strict declarations and complete-response preflight remain: ordinary `required` guarantees one or more calls, while preflight still admits only a sole legal submission or a bounded all-`navigate_code` batch and rejects mixed, unknown, malformed, post-submission, or over-budget call sets before any callback.

Keeping thinking would require an application-owned corrective provider loop for every zero-call response, including hidden transcript injection and exact replay across later FICC requests. That creates a second conversation/transcript authority, consumes provider turns behind FICC, and reverses the accepted no-manual-loop boundary. Moving to another provider API is a still larger change. Prompt-only retry remains nondeterministic. These alternatives are disproportionate when the same current endpoint/model accepts the exact provider-supported non-thinking required-tool combination.

This correction changes the Story 12.3 Worker wire and the source-free capability gate only. Streaming, endpoint/model/key, projected strict declarations, ten service turns, serial complete-response preflight, durable navigation reservation, two submissions, zero SDK retries, all byte/time limits, local result authority, atomic persistence, privacy, and sibling Chat/provider-health clients remain unchanged. The Story specification's thinking-specific FR-062/SC-015 clauses must be narrowed to the current Worker contract: require disabled thinking plus required tool selection for this path, preserve complete ordinary assistant call/content and matching tool-result continuity, and retain streamed raw-activity/absolute-deadline guarantees. No host or system change is needed or authorized.

## 2026-08-25 r18 delta audit: required selection is not single-call selection

T084 r18 passed the refreshed source-free gate and reached the approved DeepSeek V4 Flash beta route with the byte-identical streamed non-thinking request, exact two strict declarations, and `tool_choice:"required"`. DeepSeek returned HTTP success and a completed streamed response, but the whole-turn preflight classified the complete result as `MultipleFunctions` before any callback. PostgreSQL retained tool-attempt high-water zero, zero receipts, and zero Documents; no later job was sent. This is therefore not endpoint, authentication, network, schema, timeout, wire-budget, database, host, or system failure.
