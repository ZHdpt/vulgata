## Authorized settlement correction and verification

### Causal diagnosis

The user's subsequent instruction explicitly requests removing `_stderrPump.WaitAsync` if that is the cause and continuing execution. The focused native/controlled run at `TestResults/isolation-cb56afe2c7be40149a547c179fa60d8b/results.trx` selected three cases and failed all three for the intended counterexamples. Native observations show the tracked process alive during initialization/navigation and after the initial graceful wait; after the owned kill, the next wait begins with **`HasExited=true` and `StderrPumpCompleted=false`**, then times out. The two focused real-process tests separately prove exit code 7 is hidden by a blocked diagnostic reader and that disposal fails to stop that reader.

The pinned Windows bootstrap uses `subprocess.run` to wait for the Java invocation; it does not use the POSIX exec branch. The bounded correction is therefore authorized in `PreparedJdtProcessLauncher.cs`: process-exit confirmation must not wait for diagnostic EOF, while disposal independently cancels/closes and observes the diagnostic reader. Existing exit confirmation, owned-state checks, 30-second grants, shutdown limits and host policy remain. The shared AnalysisAdapter and host profile are unchanged. The final combined native result below supersedes the historical blocker.

The corrected run at `TestResults/isolation-86f343a0f8cb4f51bd08056b6184c321/results.trx` selected three cases: both focused process/stderr tests passed, while combined native cleanup failed. The post-kill OS wait now completed in zero milliseconds with the parent exited and diagnostic pump still pending. The later diagnostic at `TestResults/isolation-864f7536ef5a40b6be14131402f1c507/results.trx` identified the next failure precisely: `File.Delete` denied access to the owned `temp/jna-46826331/jna2942127636830338908.dll`. This is distinct from the removed stderr wait. Read-only inspection found no ReadOnly/reparse attributes in the previously retained state. Child-exit diagnostics are required before choosing a cleanup repair; no deletion retries, attribute clearing or timeout extension were introduced.

The descendant diagnostic at `TestResults/isolation-8e5d3e56baee4a02a5e472cb1cd8afc5/results.trx` establishes the remaining cause. Before termination, exact launched root PID 4272 had conhost PID 45460 and Python PID 44816; Java PID 49444 was Python's child. After `Kill(entireProcessTree: true)`, the root, conhost and Python had exited, while the retained Java handle still reported alive. It remained alive after a bounded three-second observation, and deletion of its owned JNA DLL failed. This requires settlement of the actual captured descendants, not stderr EOF or a deletion retry. The bounded continuation stays within `PreparedJdtProcessLauncher.cs`: validate and retain descendant handles before termination, terminate those exact handles deepest first, and share the existing wait deadline across parent and descendants. Failed capture/wait preserves owned state; no host profile, lease or shared AnalysisAdapter change is introduced. Independent design review accepted this approach conditionally on code review and regression/native GREEN.
