# OCT-BUSINESS shared contract proposal v1

Planning contract; no compiled API exists yet. Business owns these semantics and future Core/Shared types. The integration owner distributes one compiled checkpoint; consumers must not invent alternate contracts/schemas. Method/type names below are proposed, not claims about current APIs.

## Identity and ownership

- `OctoberKnowledgeBinding`: exact canonical database identity, TargetId, BatchId, setup selection digest. Derive from trusted `IOctoberHistoricalBoundSetupData.Snapshot`; never model arguments or arbitrary connection strings.
- `DocumentHandle`: BatchId, PublicationId, LogicalDocumentId, DocumentVersionId, optional SectionId. The host resolves its database binding independently. A handle grants no authority.
- `PreparedOrigin`: RepositoryId, RootBindingIdentity, relative file path, verified content digest and prepared-source version. No synthetic Git hash, ScanRun or physical path in public data.
- `Contributor`: source Repository/root binding or advisory scope/record/version/content digest, including associated System/Repository where applicable. Store the complete transitive contributor union, not just citations. Advisory prose retains `AdvisoryNotSourceProof`.
- `KnowledgeReadSelection`: opaque application token for exact binding/publication, authenticated subject, fixed purpose, mode, requested Repository scope and expiry. No captured permission boolean. Request/Chat turn owns lifetime; exact historical reference opening creates a fresh selection for the same publication.
- Canonical payload schema version is 1. Canonicalization sorts object keys and set-valued identity collections ordinally, normalizes repository-relative path separators, preserves ordered narrative/branch arrays and text, and hashes UTF-8 bytes with SHA-256. Reject duplicate keys, non-finite numbers, unsupported versions and ambiguous normalization. Never canonicalize away source-significant text. All mutation digests include schema, operation kind and complete bound identity; never include credentials.

## Claim qualifications and consumer preservation

Every material section or statement group carries a stable ClaimGroupId, text, qualification (`SourceSupported`, `Advisory`, `Hypothesis`, `Uncertain` or explicitly `Mixed`), exact source/evidence/context references, and any conflicting or missing evidence. Mixed is permitted only with explicit attribution of which clauses have which support; otherwise split the group. A document-level AdvisoryNotSourceProof tag or contributor list alone is insufficient.

CL acceptance validates the qualification structure and references. BL synthesis receives these groups with their qualifiers, retains the source/context distinction and maps each material output group to supporting input groups. Unsupported upgrades are rejected as invalid references/qualification structure; model narrative usefulness remains separately evaluated. A source action such as acquiring a lock cannot become a proven business motive or duration solely because advisory context suggests it.

Reading/search excerpts and derived Markdown retain the relevant visible qualification next to the affected statement, not only in a hidden provenance footer. Business projections retain safe advisory/hypothesis/unknown labels while omitting technical CL/source identifiers. Chat receives qualified groups and must preserve material qualifications in its answer/history summaries; Chat owns that rendering behavior, and the shared fixture tests its input semantics. Acceptance does not make all content source-proven.

## Producer-only acceptance and completion

Proposed Core boundary: `IOctoberKnowledgeWriter.AcceptCompletedFileAsync`, `LookupOperationAsync`, `PublishSelectionAsync`. Scan receives a narrow trusted adapter; none is registered as a model tool or public write API.

1. Scan admits one exact selected file using trusted setup/source binding and owns an in-process admission identity. The model receives only analysis inputs.
2. Scan's finalizer assembles a canonical whole-file proposal: semantic unit keys/selectors/parent keys, structured CL sections and Source Anchors, observations, Uncertainties, contributor set and whole-file coverage disposition. Knowledge derives permanent identities from batch + Repository/root binding + normalized relative path + canonical semantic selector (not line ranges, tool symbol IDs, worker UUIDs or job IDs). CL Logical Document follows its Code Unit; version identity is allocated once with operation result. No cross-batch lineage implied.
3. Scan's private application state seals `Completed(digest)` only after full assembled success, no pending tools, valid provider termination and complete required file coverage. The non-model-constructible capability binds issuer/admission/attempt/batch/file/digest. **It proves analysis completion, not current permission to write.** Its digest remains immutable, while separate process-local attempt eligibility can irreversibly become fenced. A controlled fixture has its own explicitly labelled issuer only in test composition.
4. Before opening a new transaction, Knowledge validates the capability and current attempt eligibility, binding, live operator/contributor authority, exact digest, verified file anchors, nonambiguous semantic keys/parents, unique structured sections and coverage. A fenced/expired attempt cannot begin a new write even with a valid completed capability. Missing source validation is failure. Nested/shared anchors are allowed; whole-file zero-unit acceptance requires an explicit successful no-unit disposition.
5. Stage operation result, manifest, units, immutable CL/sections, observations/Uncertainties/contributors and coverage in one transaction. Unique keys settle duplicate writers; at most one accepted digest per admission. Immediately before commit submission, the writer and Scan use **one process-local per-attempt commit guard**, shared with fencing: recheck the fence, applicable drain/run deadline, hard-stop state and fresh live authority; failure rolls back staged rows. The guard serializes effective fence installation against marking/submitting this exact transaction as CommitInFlight. Hold that guard through commit submission, with no unguarded await/work between its final checks and submission; then await/settle the database outcome. A precheck at seal issuance or transaction entry alone is insufficient. Expiry is checked from the host's monotonic deadline, not merely a timer callback that might run late. Hard-stop/revocation cancellation also reaches in-flight database I/O. No durable completion/receipt framework or independent Business stop policy is added.
6. Every retry first checks durable operation `(BatchId, Kind, OperationId)` and compares the canonical payload digest. Identical returns exact committed identities subject to current disclosure authority; different returns Conflict. A commit transport/cancellation failure is resolved through that operation on a separate bounded lookup. Unavailable lookup returns CommitIndeterminate, never proof of absence. No provider rerun. A restarted process can look up a result; it cannot reconstruct a fresh completion capability from old draft JSON. No durable restart protocol is promised.

Statuses: Committed, AlreadyCommitted, Conflict, InvalidProposal, NotCompleted, StaleOrFenced, Denied, AuthorityUnavailable, CancelledBeforeCommit, StorageUnavailable, CommitIndeterminate, LogUnavailable. No exception text or foreign identity leaks in consumer-facing responses.

### F1 — Canonical stop/acceptance ordering and Scan adoption

The minimal rule is **current eligibility at serialized commit submission**, not an irrevocable completion seal and not cancellation-as-proof-of-rollback. Scan owns the process-local stop/deadline/fence state; Business owns the transactional writer. Both use the same attempt guard. Freeze waits until every potentially committing operation is settled; the process-local guard is not a database commit receipt.

Counterexample: `seal issued -> graceful drain expires/fence -> transaction begins`. The completed digest remains valid evidence of analysis, but the entry check rejects the fenced/expired attempt. No transaction begins. If staging began earlier, the final guarded check instead rolls it back; no commit is submitted. Timer delay or an old capability cannot bypass expiry.

| Event/order | New acceptance or provider work | Existing database operation / freeze |
| --- | --- | --- |
| First graceful stop; active attempt still within drain and run budget | No new file admission; existing active attempts may finish and submit acceptance only while eligible. The first stop itself is not a fence. | Settle writes, then freeze exact accepted subset plus gaps. Finalization may run only under the original remaining execution scope. |
| Drain expiry/effective fence before commit submission, including seal -> expiry -> transaction | Reject new write or roll back staged transaction as StaleOrFenced; do not submit commit. | Record stopped gap only after confirmed noncommit/rollback. No late acceptance enters corpus. |
| Hard cancellation before submission | Fence attempts, reject commit and all new provider calls; cancel owned outstanding work. | Roll back staged transactions; skip finalization. Retain already committed history. |
| Observed authority loss or authority check unavailable before submission | Denied/AuthorityUnavailable; completion grants no exception. Fence/cancel affected work, no further provider disclosure. | Roll back staged transaction; no publication/finalization under lost authority. |
| Commit already submitted before fence, hard stop, expiry or newly observed authority loss | No additional writes/calls permitted by that old capability. Cancel in-flight I/O where possible. | Submission is not success. DB may commit or roll back; exact lookup decides. A later physical commit is possible after an already-submitted commit, so do not assert that cancellation proved rollback. Recheck authority before disclosing any result. |
| Already committed before stop | No regeneration or replacement operation. | Preserve immutable result; identical lookup/replay returns exact handles only under current disclosure authority. Graceful freeze can include it after settlement; hard stop still skips finalization. |
| Commit acknowledgement ambiguous | No retry generation, replacement write, success claim or freeze. | Bounded exact operation lookup independently of cancelled work I/O, with current authority. If an original operation may still commit, a momentarily absent row is not proof of noncommit. Resolve committed or confirmed rolled-back/never-submitted; otherwise remain CommitIndeterminate. |

Scan must adopt these exact meanings in its C0 completion/fence/freeze contract and controls: a completed proposal may still become ineligible; an effective pre-submission fence denies commit; an already-submitted commit can only be classified by settlement/lookup. Its current shorthand 'fence before commit prevents acceptance' must distinguish commit submission from eventual database visibility. Scan's active-attempt drain expiry does not cancel a separately allowed finalization phase; hard stop, authority failure or the run deadline does. Consumer concurrence is **pending**, not claimed by Business's local review.

The same host stop/deadline eligibility and fresh authority apply to new PublishSelection commits, with their own operation identity and phase eligibility. Hard stop/lost authority bars a new publication; an already-submitted publication follows identical settlement/lookup rules. No ordinary Knowledge reader needs a generator execution scope.

## Fixed publication

`PublishSelectionAsync` takes an explicit manifest/version set, relationship selection, flow dependency sets, coverage dispositions, expected corpus digest and unique operation key. Never enumerate latest rows at commit time.

- **F5 / early S2-B0:** B0 can publish a nonempty CL-only fixed selection immediately from settled accepted manifests and honest coverage, with no resolution, flow, BL or Business provider call. PublishSelection accepts empty relationship/flow/BL sets and does not require B1/B2 completion. A zero-unit-only result has coverage but no readable CL and must not claim the one-real-CL milestone. Scan owns Generate selection of this early path; Business supplies publication and exact reads. B2 later creates a separate immutable CL+BL publication; it never mutates B0. Hosts explicitly choose B2; readers do not follow latest.
- Natural finish or **graceful operator stop** closes further admission/dispatch, settles active completion/acceptance operations and performs exact operation lookup for ambiguous replies. Scan records each selected file as accepted, completed-zero-unit, failed, cancelled or unprocessed; the latter dispositions include a reason and coverage gap. Files never dispatched still appear in the inventory coverage. A fence/expiry winning before guarded commit submission forbids a new manifest even after a completion seal. A previously submitted commit must settle under F1 before freeze; it is not presumed accepted. No late operation may enter the frozen corpus.
- Freeze then pins exactly the settled accepted subset plus all terminal/unprocessed dispositions. A settled graceful stop is eligible for bounded resolution/BL with honest partial coverage; it need not resume the stopped analysis. Paused work, active unsettled writes or CommitIndeterminate remain non-finalizable. Whole-run abort or loss of authority does not authorize further provider work; graceful stop-of-analysis and abort are distinct host controls, owned by Scan. Accepted external manifests can contribute without claiming complete external coverage.
- Each flow group pins exact root, membership, relationships, Uncertainties and all synthesis inputs. Every selected resolution item must have an accepted or explicit unresolved/failed disposition before BL synthesis.
- Validate every endpoint and dependency belongs to the exact fixed corpus/batch, or is an explicitly recorded unresolved external reference (never a fabricated Document). Reject contradictory duplicate versions for a Logical Document within one selection.
- Commit publication membership, flow BL/dependencies and selected relationships/Uncertainties in one transaction. Failed BL is not included; other completed flows may publish with honest gaps, preserving per-flow coherence without a global-success barrier. Never label the failed flow complete.
- Immutability applies to content, memberships, relationship/evidence versions and historical dependency targets. Authorization narrowing affects visibility, not accepted historical truth.

## Consumer reads

Proposed ports: `IOctoberKnowledgeReader.OpenReadSelectionAsync`, `SearchAsync` (empty query is browse), `ReadExactAsync`, `GetRelatedAsync`. `IOctoberKnowledgeDisclosurePolicy` is mandatory for every implementation.

- Default page size 20, maximum 100; lexical query maximum 512 Unicode characters. Stable ordering is `(LogicalDocumentId, DocumentVersionId)` ordinal with publication fixed. Search uses normalized lexical matching of permitted title/section text, without vector infrastructure or relevance-score authority.
- Exact reads return at most 64 KiB UTF-8 text/JSON projection per response; longer Documents use section/chunk continuation without dropping text. Section IDs are stable within the version; chunk boundaries preserve valid UTF-8. Whole Document read capability remains complete through bounded continuation, not silent truncation.
- Related reads are directed one-hop selected REFERENCES or GENERATED_FROM with exact endpoints/meaning, maximum 100 edges/page. Graph traversal is Explore-owned and must repeatedly use these permitted edges; layout never invents accepted edges.
- A protected cursor binds database/batch/publication, subject/purpose/mode/scope, normalized query, operation, order, page limit, exact section/chunk position and expiry (default 30 minutes). Tampering/mismatch/expiry produces a safe invalid-continuation result, not alternate selection.
- Filter authorization and mode before returned ordering, counts or page metadata. Never return hidden totals or a cursor solely because hidden items exist. If a server work cap prevents determining the next permitted page, return safe `ReadBudgetExceeded` without a data-dependent hidden count; do not pretend full exhaustion. Materialize bounded results, then recheck all returned contributors immediately before disclosure. Stable membership does not guarantee visibility stays unchanged; a changed permission can yield unavailable/restart, never leak or infer a missing item.
- Exact absent, unpublished, out-of-scope and denied handles all return metadata-free Unavailable. Business CL-only browse is empty without CL counts or cursor. Operational outages may return sanitized UnavailableService without object details. Cancellation returns no partial page.
- Public results include authorized exact handle, kind/title/sections, qualified provenance, coverage/Uncertainties and allowed related metadata. Business projection omits CL handles/source paths/technical endpoint identifiers, including GENERATED_FROM targets; it can retain safe business narrative and BL-to-BL references. All hidden CL/advisory contributors still authorize the BL as a whole.
- Chat records only handles successfully read in that turn and revalidates before footer/history disclosure. Business supplies exact read results and live revalidation; Chat owns the per-turn read ledger and stream behavior. Explore owns one shared reader route; no route is invented by this lane.

## Concrete live ordinary-reader policy

This plan chooses coarse existing-role access, not new per-user Repository ACLs. Existing roles and entities provide no fine-grained reader permissions (PRD FR-1.4). Scope selection can narrow permission but cannot override live account or contributor denial.

1. Host supplies the browser subject and current authenticated security-stamp binding; reject absent/foreign subject. Fresh Identity lookup must find an eligible account, permit sign-in, not locked out, match current security stamp and include a current Administrator, SystemOwner or User role. Do not trust a cached circuit role flag. All three roles can read; no stored operator identity or SystemOwnerAssignment requirement for Knowledge consumption.
2. Host supplies an explicit selected database/batch/publication. Verify canonical database identity, batch selection digest and publication membership against persisted records, independently of operator-only `IOctoberBatchSelector.BindAsync`. No connection supplied by the browser/model. Missing/mismatch is unavailable; ordinary Web/administration remains operational.
3. Requested scope must be a subset of that publication's Repository scope and persisted setup. A returned object's entire source/advisory contributor union must fit the requested scope and persisted binding. Check each live Repository exists, still has the bound System association (or still standalone), and any bound System exists. Check advisory records remain accessible under their Global/System/Repository scope; selected snapshot hash/provenance stays exact. A deleted/moved contributor or removed context record makes dependent composite content unavailable. Edited advisory text does not rewrite the historical snapshot.
4. Purpose is a host-issued allowlisted Knowledge purpose: Reader, Chat, Graph, or producer-only Resolution/Synthesis. Reader/Chat/Graph never grant source-tool authority. Business/IT is fixed in the selection; Business authorizes only BL projections.
5. Recheck at operation entry and after materialization, and before provider disclosure in Resolution/Synthesis. Authority-store errors/timeouts fail closed. Permission revocation never relies on a publication token expiry. Already transmitted bytes cannot be retracted; subsequent calls/stream/history disclosures recheck via consumer contracts.

The labelled disallowed contributor fixture uses a Contributor outside requested scope or with removed live records, and tests a BL that cites only an allowed contributor while relying on the disallowed one. Additionally test user role removal, lockout/security-stamp change and contributor movement. If product requires different ordinary-user Repository entitlements, stop before implementing disclosure and obtain that policy; do not invent an ACL table or silently reuse management ownership.

## Resolution and synthesis limits/semantics

Initial process-local configurable limits: 32 candidates per observation; 64 observations per inquiry batch; one model inquiry per unique `(corpus digest, question, candidate/evidence/policy fingerprints)`; two total provider attempts before any accepted/visible result, within 120 seconds per inquiry; 256 nodes, 512 directed edges and depth 16 per flow slice; two synthesis attempts within 180 seconds per flow. A run also has explicit total call/time budgets supplied by Scan; absent budgets block dispatch. Retries never follow a committed result or uncertain persistence reply. Limits are recorded with gaps, not universal product capacity claims.

- Candidate ranking may reduce inquiry size but must report unexamined candidates as not evaluated; it cannot make the remaining candidate proven. No hardcoded pair, service map or protocol identity recipe.
- Positive acceptance checklist: exact caller/provider version endpoints; source-backed caller operation/mechanism and provider role/operation; compatible logical namespace/binding evidence that actually connects them; supporting and opposing evidence assessed; no decisive unresolved contradiction. Distinguish static linkage from deployment certainty. Unknown mechanisms/bindings remain Uncertainties.
- The model receives bounded accepted evidence as input, no new source/tool surface. Proposals cannot commit Edges. Domain validation rejects unsupported identities or invented supporting evidence; unresolved cases retain outcome/limitation rather than retries until confidence rises.
- Roots are exported operation/handler/schedule/declarative workflow/explicit selected Code Unit with source evidence. Root identity derives from batch + root Code Unit + root kind/selector. Distinct roots remain separate even with shared helpers or cycles; local-only roots qualify. Record visited set and all bounds/frontiers.
- Pin exact CL/relationship/Uncertainty/advisory versions before synthesis. Additional authorized CL actually read enters both dependency set and contributor union. Use an input/read ledger; include all model-visible evidence conservatively, not just model-reported citations. BL preserves conditions, alternatives, data/state effects and gaps and cannot assert new authoritative relationships. Business prose omits raw technical details while internal dependencies retain them.
- Provider profile/credentials come from explicit generator selection via Scan; binder validation alone is not a client. Use installed agent/provider integration with externalized prompts. No failover, arbitrary remote provider choice or added package without review.

### F2 — Host-supplied execution/admission/accounting scope

Every Business matching/inquiry/synthesis **provider attempt**, including a retry, must acquire Scan's injected process-local execution scope before contacting the provider. This is a required semantic port in the owner-published shared checkpoint (proposed `IOctoberExecutionScope.AcquireProviderAttemptAsync`), not permission to build another scheduler, service or independent semaphore pool.

- Host binds the scope to run, finalization operation, purpose/phase, authorized provider profile, **one configured cap shared with file Workers**, remaining run/finalization request/usage/time budgets, host provider request/rate admission, absolute monotonic deadline and hard-stop cancellation. Business can request smaller bounds; it cannot select a different scope/profile, reset counters or extend a deadline.
- Acquisition queues within the same remaining deadline or returns a bounded denial. The host coordinates the same cap, provider request/rate admission and request/usage reservation before dispatch; recheck eligibility and rate admission on grant and immediately before the provider send. A rate-delayed call stays queued within the original deadline, and a rate-denied/expired grant sends nothing. Business cannot reset or bypass the host limiter or create an independent local rate allowance. Finalization orchestration itself holds no provider permit while waiting for children: at cap=1, concurrent inquiries queue and run serially without a nested-permit deadlock. Per-call numeric defaults above further restrict, never replace or multiply, the host limits.
- Link provider I/O to the granted deadline/hard-stop signal. First graceful stop permits active-file drain calls and, after settlement, the explicitly allowed Business phase within original budgets. Drain expiry fences the affected file attempts; it does not manufacture a new allowance for Business. Hard stop, authority failure or exhausted run deadline denies queued/new calls, cancels active attempts and prevents acceptance/publication of late returned proposals under F1. A response received after hard stop cannot become a new accepted result.
- Settle each dispatched attempt exactly once with correlation, actual request count, reported token/cost usage when available, explicit unknown usage otherwise, elapsed/wait time and terminal outcome (including cancellation/transport failure). Unknown is never zero: retain a conservative reserved usage charge, or refuse further usage-constrained calls when remaining allowance cannot be established. No accepted result or unclear persistence acknowledgement causes another model attempt.
- Dispose/release the granted permit only when its provider attempt/transport has settled or been confirmed disposed; never release early to admit overlapping work. An unconfirmed cancellation remains an owned outstanding/failed-cleanup condition; stop further dispatch rather than claim reclaimed capacity. Accounting and permit cleanup run on every outcome; repeated local settlement must not double charge or double release.
- Missing/incompatible scope is a checkpoint/runtime stop, not an invitation to instantiate a Business pool. Sharing policy/interfaces with Web does not create cross-process permits: generator controls are process-local; Web Chat has its own explicitly composed process-local execution lifetime.

Required checkpoint probes: with cap=1 and two concurrent Business inquiries, only one provider attempt is active, the other waits, counters are shared and both settle once; with hard stop during one active and one queued call, active receives cancellation, queued/late/retry calls never dispatch, a late model result is not published, usage remains actual/unknown and settlement is truthful. Also exercise a queued/rate-denied call that sends nothing until host rate admission permits it (or ends at its original deadline), a retry acquiring a fresh permit without resetting budgets/rate allowance, and missing scope failing before dispatch. Probes use controlled transports and the initial owner contract/fixture, not paid calls or completed consumer production implementations.

### F2 — Completed Business result handoff lifetime

The Business-owned `IOctoberBusinessHandoffLifetime` is a narrow companion to the
host execution scope. Its cached `HandoffCancellation` is the original run's
stop/deadline signal and remains observable after an individual provider attempt
has settled and its lease has been disposed. Disposing an attempt must neither
erase that signal nor grant a new lifetime.

`CheckHandoffEligibility(runId, finalizationOperation, providerProfileId)` is a
synchronous host check of the exact identities and the eligible CL-and-BL Business
phase. Wrong identities, hard stop, original deadline expiry, host-scope disposal
or authority denial fail closed. Stop/disposal/denial is monotonic for that
lifetime: a later call cannot revive a completed result after invalidation.
Consumers retain and check the original lifetime before returning a completed
proposal; missing or incompatible lifetime is unavailable, not implicit success.

This check is not provider admission and reserves no permit, request, rate,
token or time allowance. Unknown usage, unavailable capacity or exhaustion of
budgets for a *future* provider call alone does not invalidate an already completed
result whose original handoff lifetime remains eligible. Settlement/accounting
still records actual or explicitly unknown usage, and F1 independently rechecks
eligibility at durable submission. No fresh allowance, regenerated proposal or
acceptance authority follows from this interface.

## B2 canonical finalization selection and identities

The accepted bounded Scan/Business agreement uses the existing `FinalizationRequest.CanonicalPayloadDigest`; nullable non-positional `Selection` preserves constructor compatibility but missing Selection or default Roots is invalid. Explicit empty Roots permits truthful durable NoContent and zero provider calls, not proof that no source roots exist. Maximum roots is256; duplicate stable `(batch, unit, kind, selector)` identities, conflicting versions and enlarged flow limits are rejected. Actual corpus membership and original live dispatch authority remain owner/host checks, not hash-helper authority.

`OctoberBusinessFinalizationPolicy` is the single owner serializer/hash implementation, schemaVersion1. Provider fingerprint envelope domain is `october/business-provider-configuration/1`, with configuration fields SourceIdentity, Precedence, ProfileName, ApiType, exact Endpoint spelling, Model and CredentialReferenceId. The reference is a nonsecret identifier, never credential plaintext/ciphertext/hash. The fingerprint does not identify rotated credential contents; the host binds the frozen actual client/credential lifetime separately. Request domain is `october/business-finalization-request/1`, binding Operation, Corpus and Selection (roots, narrowed limits, RunId, profile ID, configuration fingerprint, prompt digest and token ceiling), excluding ExecutionScope and the self digest. Root sets are sorted by canonical stable identity; raw narrative arrays retain order.

Outcome domain is `october/business-finalization-outcome/1`, binding the exact request digest, selection, original synthesis proposals and explicit terminal Failed/NotEvaluated dispositions. Every selected exact root occurs once across the completed/disposed partition. Outcome self digest is excluded. The persistence owner will reload trusted inputs and derive accepted content, IDs and complete typed dependencies; this transport shape is not acceptance or model authority. Lookup replays an exact persisted result only; missing/indeterminate lookup cannot authorize generation, owner-death or a restarted run. Scan retains single-flight, F1 and shared execution budgets; the256-root cap grants no provider allowance. No schema, S3 activation or runtime permission follows from these declarations.
## Shared diagnostic and dialogue boundaries

Business owns a sanitized append-only `log.md` writer: UTC timestamp, correlation/operation ID, sanitized target token and outcome, no raw content/query/secrets. Cross-process writes serialize under an owned file lock. A failed append returns LogUnavailable; committed mutations remain recoverable by exact lookup and a retry never regenerates. Log is not transaction authority. Runtime must supply the owned path; no machine/global configuration change.

Chat supplies conversation owner, fixed publication/scope/mode, ordered turns, one active turn, terminal completed/interrupted/failed outcome, exact turn-read references, and idempotent save/lookup semantics. Business implements only their shared persistence mapping after contract agreement; Chat validates generation completeness and history usefulness. Schema constraints: unique `(ConversationId, TurnId)`, monotonic sequence, unique active turn per conversation, outcome digest conflict check, owner+selection binding and exact reference foreign keys. Completed replay does not generate; partial outcomes are not completed history. No reconnect/summary platform in this slice. See data-model for concrete fields.

### Finalization persistence diagnostics agreement

Integrator and Scan accepted optional non-positional `BusinessFinalizationResult.PersistenceStatus` using existing `KnowledgeWriteStatus`; null is omitted and means no additional persistence observation, never confirmation of commit. Valid combinations must be checked at owner boundaries: conflicting request/outcome is Failed+Conflict without publication/content; confirmed Published/PublishedPartial/NoContent retains the exact authorized durable outcome when append fails and reports LogUnavailable; Committed/AlreadyCommitted must agree with replay state; unknown durable state remains CommitIndeterminate without invented artifacts or regeneration authority. Per-call append/replay diagnostics are excluded from immutable request/outcome identities. Fresh disclosure governs every returned handle and coverage projection.

Scan's agreed future report mapping preserves confirmed publication or NoContent and completed stage, adds `operation_log_unavailable`, and reports Execution=Failed/exit1 for log failure. It must not silently report a completely clean run or confuse known publication with indeterminate storage. This compatibility agreement grants no new provider dispatch, S3 activation or runtime resources.

### Original-run first finalization callback

The producer-only `IOctoberFlowPublicationInitialRead.ReadForOriginalDispatchAsync(CorpusHandle, OperationKey, canonicalPayloadDigest, token)` is implemented by the same owner store. `BusinessFinalizationInitialRead` has exactly these valid variants: NoDispatchResult with a non-null exact-operation authorized replay/conflict/denial result; ObservedAbsent with null Result after successful exact binding, live full-contributor authority and storage read; Unavailable with null Result when observation cannot be established. Inconsistent variants are rejected. ObservedAbsent proves only that this read observed no receipt; it is not proof no write can commit and grants no execution. Public recovery lookup remains missing/unavailable -> CommitIndeterminate. The proposed public NotCompleted marker was withdrawn and must not be used.

`IOctoberOriginalBusinessFinalizationSlot.RunOnceAsync(FinalizationRequest, Func<CancellationToken, Task<BusinessFinalizationResult>>, waitCancellation)` is privately issued by Scan only for the original live BeginGenerate admission, including reconciliation of its own tracked submitted Begin. A restarted receipt reader cannot obtain it. The host pins canonical immutable request/selection/run/operation/corpus/config and the same execution-scope instance, rejects wrong binding without invoking or stopping work, and installs the retained task while permanently consuming the slot before invoking the sole callback. That callback first performs the owner read: NoDispatchResult returns without model work; ObservedAbsent allows first work only under this independently granted callback; Unavailable performs no generation and leaves the slot consumed. No result, fault, cancellation or separate reconciliation resets it.

All callers, including the first, cancel only their wait. The callback receives only the original host stop/deadline token; Scan retains actual task/session/scope/cleanup even with no waiters. Exact duplicates join the retained task and cannot replace its callback. F1 write authority and F2 budgets still apply. Business must perform fresh owner disclosure before exposing every result; a cached task is not cached permission. These declarations add no schema, generic recovery system, ordinary-reader/UI surface, S3 execution or runtime activation.
