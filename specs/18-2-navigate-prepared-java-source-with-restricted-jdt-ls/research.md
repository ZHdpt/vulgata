# Story 18.2 Research and Decision Record

This is repository-grounded planning, not live JDT-LS qualification. Authority: `spec.md`, October proposal prepared-input/whole-root/F0 sections, October epics O-FR06/O-AR09/O-NFR01, PRD FR-4.9/15.1–15.3, architecture AD-15, Constitution I/IV/V and current source.

## Prepared source and session binding

**Decision**: Preserve integrated 18.1's `PreparedSourceContextIssuer` and `IPreparedSourceReadContext` exactly as Worker list/read/search. Story 18.2 owns a separate small trusted physical-workspace issuer/lease for JDT-LS and Story 18.3, bound to the same exact `PreparedSourceApproval` tuple plus explicit application-selected tool purpose. JDT-LS receives the selected source project root through Infrastructure only; disposable process data/configuration live elsewhere. No source copy, Git label substitution or second source registry.

**Rationale**: Story 18.1's public context has only `ListAsync`, `ReadTextRangeAsync` and `SearchTextAsync`; physical root and handle are private to Infrastructure. The accepted verifier checks batch, Repository, subject, `WorkerSourceRead`, approval/root-binding identities and operator label at issuance/use/disclosure. `WorkerSourceRead` alone does not authorize a JDT-LS or CodeGraph subprocess, so a separate current tool-purpose authorization is required. The October proposal excludes managed copy/snapshot and arbitrary roots. `JdtLsAnalysisAdapter.cs` currently offers a prepared-revision lease that verifies Git-style identity and calls `CopySnapshotAsync`; it is not the October contract.

**Alternatives considered**: Reuse the revision lease/mirror, lend the 18.1 read context's private root, or let Worker supply a workspace. All conflict with source origin, 18.1's closed interface or containment. A path lease alone does not constrain subprocess reads/writes. If the host cannot enforce a read-only source and least-privilege process profile, report the failure for architecture correction rather than quietly copying source.

## Restricted profile and result truth

**Decision**: Assume JDT-LS and Java commands are on the host `PATH`; trusted Infrastructure resolves them without a model argument, config-file executable selector, user-profile fallback or `.env`/`JDT_LS_BIN` input. If command invisibility blocks qualification, pause and report, including the possibility of a stale Codex process environment after a recent `PATH` edit. Fix no-import/no-build/no-restore settings at the adapter and qualify actual definition/reference calls, source no-write and least-privilege process behavior. Preserve zero results, missing classpath and failures as distinct observations.

**Rationale**: The user's revised executable choice supersedes earlier config-file/test-local environment selection. The currently observed `jdtls.bat` and `java.exe` on `PATH` prove command visibility only. O-FR06/O-AR09 and PRD FR-15.1–15.2 require semantic navigation evidence and explicit limits. The current protocol initializer supplies `rootUri` and `workspaceFolders`, but inspection found no evidenced disabling settings. `ParseEvidence` currently treats a null response as succeeded with no evidence. Neither proves the October profile or absence semantics.

**Alternatives considered**: Retain config-file executable paths or test-local `.env`/`JDT_LS_BIN`, count command visibility/startup as navigation success, assume current settings are restricted, or enable dependency restoration. The first is superseded by user direction; the rest underprove or exceed accepted scope.

## Trusted PATH executable selection

**Decision**: Infrastructure alone enumerates ordered host `PATH` entries for exact JDT-LS/Java names and launches only a validated absolute target. Empty/relative/current-directory entries, prepared-source and disposable tool-state roots, reparse redirection, wrong file types and entries outside approved host executable directories cannot supply the command. An untrusted first match fails closed rather than falling through to a later one. Pin canonical path, file identity and digest for the session; hold against replacement where supported and recheck immediately before launch. The fixed batch interpreter and Java child use the same approved process boundary and constrained child `PATH`.

**Rationale**: The independent P-PATH-TRUST-01 finding correctly identified that a PATH-only instruction prevents model selection but can still select attacker-controlled source or tool-state content. Windows process creation can search application and current directories when given a bare executable name, and batch launch uses a command interpreter; see [Microsoft CreateProcess documentation](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw). Explicit ordered PATH inspection followed by absolute-path launch closes that selection gap while retaining the user's PATH-only source of candidates. Host approval of an executable directory concerns process trust, not a fallback executable path.

**Alternatives considered**: Bare-name `Process.Start`, generic command lookup that may search the current directory, skipping a malicious first match to a later candidate, or trusting a lexical PATH string without checking reparse/identity. Each leaves executable substitution or search-order ambiguity. A fixed config path or `.env` selector would contradict the revised user instruction. Location validation alone does not replace the separately required subprocess isolation.

## Concurrency, lifetime and failures

**Decision**: One owned session per selected Repository, bounded issuance/queue/readiness/request/authority check/shutdown, serialized shared protocol operations until overlap is proven safe. Check exact current source approval and selected tool purpose at issuance, before and during use, and immediately before disclosure. Authority loss latches the lease closed, cancels owned activity and discards buffered results from every concurrent request. After timeout/protocol failure, settle the owned session before a new attempt. No unrelated process termination.

**Rationale**: O-FR06 and Story 18.2 acceptance require one-session ownership, serialization and bounded cleanup. The current adapter already has timeout and owned process/lease disposal mechanisms, but they are tied to the old scope and require direct-root assessment.

**Alternatives considered**: Per-Worker processes and blind automatic replay increase contention and hide uncertain outcomes.

## October JDT-LS construction seam

**Decision**: Introduce one Infrastructure `PreparedJavaNavigationContextFactory` whose trusted constructor takes bounded profile/state configuration and an injected `IPreparedJdtLsRuntime`, and whose `OpenAsync` takes the already issued `JdtNavigation` workspace lease plus cancellation. Return one context only for `Opened`; other statuses have no context. The injected runtime owns and cleans everything it starts until it successfully returns a session. The factory owns its one-session slot and any returned session until successful context handoff; on pre-return exception/cancellation it maps the status and releases the slot without pretending to dispose invisible resources. After handoff, the context owns the session; the caller retains and later disposes its separate lease. Controlled fakes can expose each phase with zero real launches. See `contracts/navigation-tool.md`.

**Rationale**: T010 stopped before writing a test because the Core navigation interface and Agent functions had no accepted Infrastructure creation/injection route. Definition review P-PARTIAL-OPEN-OWNERSHIP-01 then exposed a false assumption: a factory cannot clean process/protocol resources the runtime has not returned. The corrected handoff gives each resource an observable cleanup owner and keeps failure outcomes testable. Current `JdtLsAnalysisSessionFactory.OpenAsync(AnalysisScope)` remains tied to Profiled Revision and mirrored workspaces, which ID-L01 excludes from October grant authority. The new factory remains a small seam for lease validation, session ownership and raw-result containment. The project lesson requires exact construction/result/lifetime/cancellation before TDD.

**Alternatives considered**: Wrapping the legacy `AnalysisScope` factory would import rejected source identity/copy behavior; having tests instantiate private JDT internals would bypass the public capability; exposing physical root or runtime selection as Worker arguments would break authority. Building a broad language-server framework is unnecessary. Production runtime registration and any real Java/JDT launch stay closed until T022/T023 accepted trusted PATH/process-profile work.

## Trusted internal root use

**Decision**: Preserve the implemented `internal` `PreparedToolWorkspaceLease.UseContainedRootAsync(expectedPurpose, callback, cancellationToken)` for trusted physical-root binding, separate JDT state comparison and contained result mapping. Change its mapping input from `Uri` to the JSON-decoded, not URI-normalized raw protocol string. Reject device/extended-length, UNC, encoded syntax and noncanonical `file:` forms before parsing; only then use held-root-relative no-follow traversal to produce `PreparedSourceLocation`. No public/model path or handle is added. Story 18.3 may use the JDT-independent root binding after an updated verified checkpoint and separately authorized integration.

**Rationale**: Earlier T010/T011 work added the callback and preserved its private root handle/identity. A callback gives the trusted adapter the minimum physical binding during one bounded use, and rechecking after use invalidates derived locations when approval/root changes. The remaining `Uri` parameter cannot faithfully represent literal Windows `\\?\\` or `\\.\\` device spellings: `System.Uri` may throw or normalize before the denial seam, so the existing test obligation cannot honestly pass using a constructed `Uri`. The raw protocol string is available at JSON parsing before that loss. This callback itself does not sandbox a subprocess.

**Alternatives considered**: A public `RootPath` property, a model-visible workspace selector or an 18.1 read-context change would widen authority. A generic permanent path token would outlive the grant and permit stale reuse. Duplicating the operation in 18.3 would split source/tool authority. Testing an already constructed `Uri` for raw device syntax would establish only normalization behavior, not denial of the actual protocol input.

## Dedicated in-place CodeGraph state

**Decision**: Under the user's dedicated Vulgata-managed prepared-workspace policy, Story 18.2 adds one internal `CodeGraphPreparation`-only owned-state operation and one durable versioned ownership record outside `.codegraph`. Trusted composition supplies an `Absent` draft for an exact dedicated workspace; the coordinator persists `Creating` before an exclusive held-root create, observes the new entry's physical identity and persists `Ready` with that non-null identity before adapter use. Its `GetOwnershipViewAsync` reloads and checks the same typed record, current source/owner authority and root/entry identity for later leases and 18.3's reader; actual CodeGraph mutation separately requires current tool-purpose authority; no second descriptor or name-only exclusion is introduced. At disposition, after children/leases settle, it persists `Disposing` before bounded removal and uses injected existing source-current and tool-purpose verifiers plus ownership/readiness checks. It verifies entry absence and persists/readbacks `Removed` before success. A revoked lease or record alone is not live authority; partial create/persist/cleanup failure or uncertain transition quarantines. JDT state remains outside prepared source and 18.1 public readers remain unchanged. See `contracts/navigation-tool.md`.

**Rationale**: The current shared lease can bind a physical root and reject state-root overlap but cannot express one owned writable in-root tool-state entry. A general root-write flag would permit source or unrelated-entry mutation. The prior nullable entry record had no callable producer to commit the created identity, so a post-create check would still see null and later readers could not obtain a positive binding. A durable `Creating` prewrite and versioned `Ready` commit make partial creation detectable after restart; `Disposing` similarly prevents reuse while terminal cleanup is uncertain. No accepted dedicated-workspace store exists in current source, so trusted composition must supply and qualify one before enabling this capability. The existing `IPreparedSourceCurrentAuthorityVerifier` and `IPreparedToolUseAuthorizer` provide fresh exact cleanup authority. Current `PreparedSourceTraversal.DirectoryIdentity` includes directory last-write time; adding `.codegraph` changes that metadata and would otherwise invalidate CodeGraph and concurrent JDT leases. Story 18.2 checks stable root object identity under its held no-follow handle; Story 18.3 owns ordinary reader `ChangedInput`/traversal repair. Stable root identity does not attest source-file bytes, which need separate file observations and restricted process evidence. Parallel Development assigns this shared capability to 18.2; 18.8/18.12 consume later. No additional Repository copy is needed solely for an index.

**Alternatives considered**: A copied Repository for CodeGraph state, arbitrary declared writable entries, a lexical `.codegraph` path allowance and reusing JDT's separate-state predicate. Each either contradicts the in-place decision, broadens writes or cannot prove ownership. The lease's checked path cannot constrain native child filesystem/network behavior; Story 18.3 must separately qualify that host/process boundary before safe in-place preparation is claimed. A recoverable positive workspace owner record is a prerequisite; if no trusted manager record can be established, leave the workspace unavailable and return a design finding rather than silently adopting the directory.

## F0 integration dependency

**Decision**: Bind the shared trusted-workspace seam to integrated 18.1 `PreparedSourceApproval`, `IPreparedSourceCurrentAuthorityVerifier` and `PreparedSourceLocation` semantics without altering 18.1's issuer/context/functions or their failure/continuation semantics. Story 18.2 owns its small JDT-independent Infrastructure issuer/lease and focused tests; Story 18.3 consumes the identifiable verified checkpoint only after separate authorization. Navigation-specific context/functions and JDT-LS implementation remain 18.2-owned.

**Rationale**: Story 18.1 is integrated and verified; its read context cannot provide a physical-root lease. The Parallel Development coordination decision assigns the shared trusted workspace to 18.2 so 18.3 can use it without JDT dependencies. This is ownership, not plan/implementation approval. The current project lesson requires a callable public construction/method/result/disposal/cancellation shape before behavioral TDD; `contracts/navigation-tool.md` supplies one.

**Alternatives considered**: Duplicating 18.1's root/identity model or extending its Worker context with a physical path would create competing authority or broaden the closed Agent interface. Letting 18.3 independently create a root lease would duplicate the shared seam.
