# Story 18.2 Research and Decision Record

This is repository-grounded planning, not live JDT-LS qualification. Authority: `spec.md`, October proposal prepared-input/whole-root/F0 sections, October epics O-FR06/O-AR09/O-NFR01, PRD FR-4.9/15.1–15.3, architecture AD-15, Constitution I/IV/V and current source.

## Prepared source and session binding

**Decision**: Preserve integrated 18.1's `PreparedSourceContextIssuer` and `IPreparedSourceReadContext` exactly as Worker list/read/search. Story 18.2 owns a separate small trusted physical-workspace issuer/lease for JDT-LS and Story 18.3, bound to the same exact `PreparedSourceApproval` tuple plus explicit application-selected tool purpose. JDT-LS receives the selected source project root through Infrastructure only; disposable process data/configuration live elsewhere. No source copy, Git label substitution or second source registry.

**Rationale**: Story 18.1's public context has only `ListAsync`, `ReadTextRangeAsync` and `SearchTextAsync`; physical root and handle are private to Infrastructure. The accepted verifier checks batch, Repository, subject, `WorkerSourceRead`, approval/root-binding identities and operator label at issuance/use/disclosure. `WorkerSourceRead` alone does not authorize a JDT-LS or CodeGraph subprocess, so a separate current tool-purpose authorization is required. The October proposal excludes managed copy/snapshot and arbitrary roots. `JdtLsAnalysisAdapter.cs` currently offers a prepared-revision lease that verifies Git-style identity and calls `CopySnapshotAsync`; it is not the October contract.

**Alternatives considered**: Reuse the revision lease/mirror, lend the 18.1 read context's private root, or let Worker supply a workspace. All conflict with source origin, 18.1's closed interface or containment. A path lease alone does not constrain subprocess reads/writes. If the host cannot enforce a read-only source and least-privilege process profile, report the failure for architecture correction rather than quietly copying source.

## Restricted profile and result truth

**Decision**: Assume JDT-LS and Java commands are on the host `PATH`; trusted Infrastructure resolves them without a model argument, config-file executable selector, user-profile fallback or `.env`/`JDT_LS_BIN` input. If command invisibility blocks qualification, pause and report, including the possibility of a stale Codex process environment after a recent `PATH` edit. Fix no-import/no-build/no-restore settings at the adapter and qualify actual definition/reference calls, source no-write and least-privilege process behavior. Preserve zero results, missing classpath and failures as distinct observations.

**Rationale**: The user's revised executable choice supersedes earlier config-file/test-local environment selection. The currently observed `jdtls.bat` and `java.exe` on `PATH` prove command visibility only. O-FR06/O-AR09 and PRD FR-15.1–15.2 require semantic navigation evidence and explicit limits. The current protocol initializer supplies `rootUri` and `workspaceFolders`, but inspection found no evidenced disabling settings. `ParseEvidence` currently treats a null response as succeeded with no evidence. Neither proves the October profile or absence semantics.

**Alternatives considered**: Retain config-file executable paths or test-local `.env`/`JDT_LS_BIN`, count command visibility/startup as navigation success, assume current settings are restricted, or enable dependency restoration. The first is superseded by user direction; the rest underprove or exceed accepted scope.

## Trusted PATH executable selection

**Decision**: Infrastructure alone enumerates ordered host `PATH` entries for exact JDT-LS/Java names and launches only a validated absolute target. Empty/relative/current-directory entries, prepared-source and disposable tool-state roots, reparse redirection, wrong file types and entries outside approved host executable directories cannot supply the command. An untrusted first match fails closed rather than falling through to a later one. Pin canonical path, file identity and digest for the session; hold against replacement where supported and recheck immediately before launch. The fixed batch interpreter and Java child use the same approved process boundary and constrained child `PATH`.

**Rationale**: The independent P-PATH-TRUST-01 finding correctly identified that a PATH-only instruction prevents model selection but can still select attacker-controlled source or tool-state content. Windows process creation can search application and current directories when given a bare executable name, and batch launch uses a command interpreter; see [Microsoft CreateProcess documentation](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw). Explicit ordered PATH inspection followed by absolute-path launch closes that selection gap while retaining the user's PATH-only source of candidates. Host approval of an executable directory concerns process trust, not a fallback executable path.

**Alternatives considered**: Bare-name `Process.Start`, generic command lookup that may search the current directory, skipping a malicious first match to a later candidate, or trusting a lexical PATH string without checking reparse/identity. Each leaves executable substitution or search-order ambiguity. A fixed config path or `.env` selector would contradict the revised user instruction. Location validation alone does not replace the separately required subprocess isolation.

## Concurrency, lifetime and failures

**Decision**: One owned session per selected Repository, bounded issuance/queue/readiness/request/authority check/shutdown, serialized shared protocol operations until overlap is proven safe. Check exact current source approval and selected tool purpose at issuance, before and during use, and immediately before disclosure. Authority loss latches the lease closed, cancels owned activity and discards buffered results from every concurrent request. After timeout/protocol failure, settle the owned session before a new attempt. No unrelated process termination.

**Rationale**: O-FR06 and Story 18.2 acceptance require one-session ownership, serialization and bounded cleanup. The current adapter already has timeout and owned process/lease disposal mechanisms, but they are tied to the old scope and require direct-root assessment.

**Alternatives considered**: Per-Worker processes and blind automatic replay increase contention and hide uncertain outcomes.

## October JDT-LS construction seam

**Decision**: Introduce one Infrastructure `PreparedJavaNavigationContextFactory` whose trusted constructor takes bounded profile/state configuration and an injected `IPreparedJdtLsRuntime`, and whose `OpenAsync` takes the already issued `JdtNavigation` workspace lease plus cancellation. Return one context only for `Opened`; other statuses have no context. The injected runtime owns and cleans everything it starts until it successfully returns a session. The factory owns its one-session slot and any returned session until successful context handoff; on pre-return exception/cancellation it maps the status and releases the slot without pretending to dispose invisible resources. After handoff, the context owns the session; the caller retains and later disposes its separate lease. Controlled fakes can expose each phase with zero real launches. See `contracts/navigation-tool.md`.

**Rationale**: T010 stopped before writing a test because the Core navigation interface and Agent functions had no accepted Infrastructure creation/injection route. Definition review P-PARTIAL-OPEN-OWNERSHIP-01 then exposed a false assumption: a factory cannot clean process/protocol resources the runtime has not returned. The corrected handoff gives each resource an observable cleanup owner and keeps failure outcomes testable. Current `JdtLsAnalysisSessionFactory.OpenAsync(AnalysisScope)` remains tied to Profiled Revision and mirrored workspaces, which ID-L01 excludes from October grant authority. The new factory remains a small seam for lease validation, session ownership and raw-result containment. The project lesson requires exact construction/result/lifetime/cancellation before TDD.

**Alternatives considered**: Wrapping the legacy `AnalysisScope` factory would import rejected source identity/copy behavior; having tests instantiate private JDT internals would bypass the public capability; exposing physical root or runtime selection as Worker arguments would break authority. Building a broad language-server framework is unnecessary. Production runtime registration and any real Java/JDT launch stay closed until T022/T023 accepted trusted PATH/process-profile work.

## T022 October runtime observation and restricted launch

**Decision**: Keep the public `IPreparedJdtLsRuntime.OpenAsync(PreparedToolWorkspaceLease, PreparedJavaNavigationProfile, CancellationToken)` and add one internal October production implementation with a trusted ordered-PATH resolver, an OS-enforcing process launcher and a stdio/StreamJsonRpc protocol factory. `contracts/navigation-tool.md` fixes their constructor, typed request/result and ownership shapes. The resolver reads the running host PATH in order, rejects an unsafe first JDT or Java candidate without fallback, and returns canonical absolute path, stable file identity and digest for both or no usable result. Fixed host policy names approved executable *directories*, runtime read inputs and the fixed batch interpreter; it is not a substitute executable path. The runtime obtains the exact whole prepared root only during `UseContainedRootAsync(JdtNavigation, ...)`, keeps JDT `-data`, configuration and every redirected temporary/profile write in owned disposable state, and composes an internal launch request. Immediately before OS creation, the launcher rechecks the live lease/root object and pinned executable/interpreter identities, restricts inherited handles and child PATH, and applies the actual OS boundary to the batch interpreter, scripts, Java and descendants. It returns no process on unsafe or uncertain checks. A returned protocol session follows the existing factory/context ownership; on pre-return cancellation/failure the runtime settles process, protocol and state itself or reports `CleanupUnconfirmed`. Production composition remains closed until T023 acceptance and real execution permission.

**Initialization contract**: The single `rootUri` and `workspaceFolders[0].uri` bind the same whole granted root, while `-data` and configuration are distinct contained disposable paths. The fixed candidate setting set is `java.import.maven.enabled=false`, `java.import.gradle.enabled=false`, `java.autobuild.enabled=false`, `java.configuration.updateBuildConfiguration="disabled"`, `java.import.maven.offline.enabled=true`, `java.import.gradle.offline.enabled=true`, `java.import.gradle.wrapper.enabled=false`, `java.maven.downloadSources=false`, and `java.maven.updateSnapshots=false`. Emit the appropriate server settings on the actual `initialize`/configuration protocol path before reporting readiness; tests inspect serialized protocol input rather than an in-memory settings object. The upstream [Java extension configuration](https://github.com/redhat-developer/vscode-java/blob/main/package.json) documents these keys, while the [JDT-LS project](https://github.com/eclipse-jdtls/eclipse.jdt.ls) describes Java 21 as its runtime minimum. The exact pinned 1.61.0 server's acceptance/effect of these settings remains a T023/T024 qualification obligation; an offline flag is not proof that no import, build or restore occurred.

**Windows confinement candidate and boundary**: A Less Privileged AppContainer (LPAC) with a dedicated package/capability identity and explicit resource DACLs is a candidate for the current host. Microsoft's [AppContainer launch contract](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer) provides the LPAC creation attributes and notes its redirected profile/TEMP/TMP. The selected prepared root requires read-only child access; owned disposable JDT data/configuration/profile/temp require bounded write; fixed `cmd.exe`, the first accepted JDT script, Java and transitive runtime dependencies require read/execute. A job object bounds only owned process lifetime and does not prove filesystem denial. The launcher must establish the actual restricted child identity before executable code runs, and native probes must test source-write and unrelated-host-read denial plus descendant inheritance. T022 controlled resolver/recording-launcher/protocol tests prove request content and zero starts for unsafe candidates; they cannot qualify the OS boundary or useful JDT navigation. T023 implements the boundary; T024 qualifies real fixed-profile behavior on the declared host. Any shared host ACL, PATH or AppContainer profile operation requires separate resource authority and cannot be inferred from the story's plan/implementation approvals.

**Current host uncertainty**: Static inspection of the running host showed the first `jdtls.bat` under a user-owned writable `.local\\bin` and invoking Python against a script in another checkout; the first `java.exe` resolves to JDK 17. These are not native JDT results and do not authorize adopting the Python/external-checkout chain, a later PATH candidate or a different source origin. The pinned command's actual version, fixed interpreter/descendant chain and ability to run under an owned LPAC boundary require verification and, for shared resources or permission changes, the user's reserved decision. Until then the real runtime remains unavailable and the controlled T022 observation does not enable a process.

**Rationale**: The factory-level fake proves handoff and raw-reply mapping but cannot observe the production PATH pin, final root check, OS launch restriction or emitted initialization settings. The current `JdtLsAnalysisSessionFactory.OpenAsync(AnalysisScope)` obtains a copied/revision-bound workspace; its `ProcessJdtLsLauncher` calls ordinary `Process.Start`, and its initializer sends a workspace URI without this fixed setting set. Sharing only its bounded stdio/cleanup mechanics preserves the accepted October no-copy grant and makes T022 an honest RED at the production runtime boundary.

**Alternatives considered**: Reusing the historical injectable launcher, relying on a caller-provided `restricted=true`, checking only `Get-Command`, or treating an LPAC plan/recording fake as confinement would bypass the accepted T022/T023 proof. A general workspace or command framework is unnecessary. A different host confinement mechanism may be assessed if LPAC cannot support the selected first PATH chain without widening access; that is a plan/authority decision, never an automatic fallback to another executable or broader permissions.

## Trusted internal root use

**Decision**: Preserve the implemented `internal` `PreparedToolWorkspaceLease.UseContainedRootAsync(expectedPurpose, callback, cancellationToken)` for trusted physical-root binding, separate JDT state comparison and contained result mapping. Change its mapping input from `Uri` to the JSON-decoded, not URI-normalized raw protocol string. Reject device/extended-length, UNC, encoded syntax and noncanonical `file:` forms before parsing; only then use held-root-relative no-follow traversal to produce `PreparedSourceLocation`. No public/model path or handle is added. Story 18.3 may use the JDT-independent root binding after an updated verified checkpoint and separately authorized integration.

**Rationale**: Earlier T010/T011 work added the callback and preserved its private root handle/identity. A callback gives the trusted adapter the minimum physical binding during one bounded use, and rechecking after use invalidates derived locations when approval/root changes. The remaining `Uri` parameter cannot faithfully represent literal Windows `\\?\\` or `\\.\\` device spellings: `System.Uri` may throw or normalize before the denial seam, so the existing test obligation cannot honestly pass using a constructed `Uri`. The raw protocol string is available at JSON parsing before that loss. This callback itself does not sandbox a subprocess.

**Alternatives considered**: A public `RootPath` property, a model-visible workspace selector or an 18.1 read-context change would widen authority. A generic permanent path token would outlive the grant and permit stale reuse. Duplicating the operation in 18.3 would split source/tool authority. Testing an already constructed `Uri` for raw device syntax would establish only normalization behavior, not denial of the actual protocol input.

## JDT eligibility through the shared ownership view

**Decision**: Trusted Infrastructure composition supplies the October navigation factory with the exact application-held workspace binding and the existing `PreparedCodeGraphStateCoordinator`; it does not mint a second descriptor or rely on `.codegraph` spelling. For each request, `GetOwnershipViewAsync(binding, binding.Approval, token)` runs before any JDT protocol use. A current `VerifiedOwned` Ready record denies a request only when held-root no-follow traversal identifies the recorded physical state entry as the path's first root entry. `VerifiedUnowned` permits legitimate same-name source. After raw URI mapping, the context suppresses only locations descending from that same recorded entry identity. A fresh view immediately before disclosure must retain the same status and, for owned state, `OwnershipId`, version and entry identity; otherwise discard the entire buffered observation. Missing exact binding, store, authority or `Unavailable` view denies protocol and payload. Classification uses source/owner authority, while JDT use separately requires `JdtNavigation`; it does not borrow `CodeGraphPreparation` authorization.

**Rationale**: The current coordinator already distinguishes positively verified unowned source from current owned state and uncertainty. The present JDT mapper checks raw URI containment but cannot by itself distinguish an application-owned cache from ordinary source inside the same granted root. The trusted application owner, not the Worker or a path-name filter, has the exact workspace binding. Keeping a single view also makes 18.2 navigation and 18.3 ordinary readers agree on which physical entry is tool state. The existing two-argument factory constructor remains source compatible for earlier lifecycle fixtures, but cannot enable an ownership-eligible production context without the internal binding; a controlled test supplies an owned fixture binding/store. No production readiness follows from that fixture or a fake JDT runtime.

**Alternatives considered**: Rejecting every `.codegraph` path would hide legitimate unowned source. Assuming absence when the store is missing or a record is transitional would disclose ambiguous owned state. A second JDT-only filter or Worker-supplied binding would split ownership authority. Requiring a `CodeGraphPreparation` grant for JDT classification would conflate tool use with source eligibility.

## Dedicated in-place CodeGraph state

**Decision**: Under the user's dedicated Vulgata-managed prepared-workspace policy, Story 18.2 adds one internal `CodeGraphPreparation`-only owned-state operation and one durable versioned ownership record outside `.codegraph`. Trusted composition supplies an `Absent` draft for an exact dedicated workspace; the coordinator persists `Creating` before an exclusive held-root create, observes the new entry's physical identity and persists `Ready` with that non-null identity before adapter use. Its `GetOwnershipViewAsync` reloads and checks the same typed record, current source/owner authority and root/entry identity for later leases and 18.3's reader; actual CodeGraph mutation separately requires current tool-purpose authority; no second descriptor or name-only exclusion is introduced. At disposition, after children/leases settle, it persists `Disposing` before bounded removal and uses injected existing source-current and tool-purpose verifiers plus ownership/readiness checks. It verifies entry absence and persists/readbacks `Removed` before success. A revoked lease or record alone is not live authority; partial create/persist/cleanup failure or uncertain transition quarantines. JDT state remains outside prepared source and 18.1 public readers remain unchanged. See `contracts/navigation-tool.md`.

**Rationale**: Earlier planning identified that a physical-root lease alone could not express one owned in-root tool-state entry. The current source now implements the 18.2 coordinator and fixed SourceStorage file-CAS store; T029's owned process fixture verifies lock/CAS behavior, while production trusted owner/root admission, metadata protection and native-resource settlement remain missing. A general application root-write flag would still permit source or unrelated-entry mutation. Durable `Creating` before exclusive create and versioned `Ready` after observed identity make partial creation detectable; `Disposing` prevents reuse during uncertain cleanup. The source/tool authority interfaces exist, but no production providers are registered; a caller assertion does not supply them. Stable root object identity permits expected `.codegraph` parent metadata change while rejecting replacement; Story 18.3 owns ordinary-reader repair and actual native effects. No extra Repository copy solely for indexing is needed.

**Alternatives considered**: A copied Repository for CodeGraph state, arbitrary application-declared writable entries, a lexical `.codegraph` path allowance and reusing JDT's separate-state predicate. Each either contradicts the in-place decision, broadens application writes or cannot prove ownership. Preventive OS denial for the pinned native CodeGraph child is outside the user's narrow direct-process choice; the lease's checked path cannot constrain that child's filesystem/network effects. Story 18.3 must observe actual writes, stop native readiness on out-of-`.codegraph` or source/configuration/hook changes, and report remaining external/network uncertainty. A recoverable positive workspace owner record is a prerequisite; without trusted durable composition, leave the application capability unavailable rather than adopting a directory by name.

## Production binding and settlement decision

**Decision**: Story 18.2 composes the existing typed ownership record and fixed SourceStorage file-CAS store through one internal source that accepts only the trusted operator-admitted 18.1 grant and application-selected tool purpose. It rechecks existing current-source/tool interfaces, observes no-follow root identity and derives workspace owner from selected-host principal/ACL evidence; it rejects unprotected metadata or an uninitialized/ambiguous ledger. A process-local registry registers leases and real JDT/18.3 resource owners, latches new-grant closure before disposition and asks live resource probes for child-tree, protocol, call and handle settlement. The existing coordinator owner/readiness verifier consumes the closed, settled registry state. Persisted Ready after restart is initially unknown until independent prior-generation settlement is evidenced. The exact callable shape is in `contracts/navigation-tool.md`.

**Rationale**: `Program.cs` currently registers only an optional composer; T029's assessment finds no production workspace binding supplier, owner/readiness verifier or protected metadata configuration. The fixed file-CAS store and controlled T029 cross-process lock/CAS checks establish transition mechanics, not current operator ownership, host protection or native children/handles. `IPreparedCodeGraphWorkspaceOwnershipVerifier.VerifyDispositionReadyAsync` is currently an injected boolean-returning check; without a producer that atomically closes admission and inspects live resources it is insufficient to authorize deletion. Story 18.3's MCP disposal and parent PID exit cannot establish descendant/handle settlement. O-NFR01, AD-3/15 and FR-011/012 require exact grant ownership and fail-closed unavailable outcomes. The direct CodeGraph child still inherits host filesystem rights, so this metadata design does not claim preventive OS protection against it.

**Alternatives considered**: A caller `dedicated` flag or owner string, a second ownership descriptor, a new DB/schema/root, copying source for the index, an in-memory empty registry after restart, and parent-PID/MCP-disposal-only readiness each lack the required authority or settled-resource proof. If the selected host cannot provide a protected dedicated root/SourceStorage child and one active owner without a new architecture or access decision, keep the capability closed and return to root. Actual pinned JDT process/profile, CodeGraph child settlement and operator-prepared Repository qualification remain separate prerequisites.

**T031 callable correction**: The accepted borrow/close registry methods had no construction or Closed-to-Open operation, so a test author could not produce behavioral RED without inventing API or a private-state helper. Keep the same typed ownership record/store and make registry construction explicit: current source/tool verifiers, existing store, fixed SourceStorage policy, selected-host verifier, prior-generation settlement verifier and trusted admission/disposition time bounds. `AdmitAsync(binding,purpose,token)` checks exact authority and store, obtains a scoped no-follow root/metadata/app-only mutex hold from `VerifyAndHoldAsync`, then publishes `Opened` only after final checks. It disposes partial holds and stays Closed on denial, cancellation or uncertainty. The host verifier also supplies a preliminary `ObserveAsync(grant,policy,token)` for the later binding producer; that observation is not use permission. T031 constructs a registry with controlled providers and calls admission directly before T033's binding source exists. A real selected-host adapter and actual previous-generation settlement remain separately qualified; controlled fakes cannot authorize production. Same-process store progression retains immutable ownership key with fresh versions, while a restarted Ready remains Unknown without independent resource proof. Closure of new grants does not revoke current CodeGraph-purpose authority needed during verified disposition.

## F0 integration dependency

**Decision**: Bind the shared trusted-workspace seam to integrated 18.1 `PreparedSourceApproval`, `IPreparedSourceCurrentAuthorityVerifier` and `PreparedSourceLocation` semantics without altering 18.1's issuer/context/functions or their failure/continuation semantics. Story 18.2 owns its small JDT-independent Infrastructure issuer/lease and focused tests; Story 18.3 consumes the identifiable verified checkpoint only after separate authorization. Navigation-specific context/functions and JDT-LS implementation remain 18.2-owned.

**Rationale**: Story 18.1 is integrated and verified; its read context cannot provide a physical-root lease. The Parallel Development coordination decision assigns the shared trusted workspace to 18.2 so 18.3 can use it without JDT dependencies. This is ownership, not plan/implementation approval. The current project lesson requires a callable public construction/method/result/disposal/cancellation shape before behavioral TDD; `contracts/navigation-tool.md` supplies one.

**Alternatives considered**: Duplicating 18.1's root/identity model or extending its Worker context with a physical path would create competing authority or broaden the closed Agent interface. Letting 18.3 independently create a root lease would duplicate the shared seam.
