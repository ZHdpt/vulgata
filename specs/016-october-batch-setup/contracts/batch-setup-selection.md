# Shared October Setup and Selection Contract

This describes Story 18.4's generator/Web boundary, not an HTTP route or the Story 18.1 source contract. Names are conceptual until tasks and implementation. Both hosts must use the same Core policy and Infrastructure setup writer/selector rather than separate persistence rules.

## Programmatic setup request

Caller-controlled inputs: an allowlisted target ID, exact nonempty batch ID, chosen System/Repository identities (System optional for a standalone Repository), and selected applicable Global/System/Repository context references. A caller-supplied operator subject, connection string, unlisted target or physical source path is never authority. The source association is accepted only through the integrated Story 18.1 contract after reconciliation; no setup request grants a root, Git revision or tool by itself.

The ordinary Web management endpoint obtains the operator from its existing authenticated Identity principal and checks live `ManagementAccess` (Administrator or SystemOwner backed by `UserManager`). It validates the target ID against deployment-operator-owned configuration, not database reachability. It checks a System member through current System-owner visibility and Repository membership. For a standalone Repository, it requires current `ManagementAccess`, an existing Repository with `SystemId == null`, and no fabricated System/owner. It then issues a short-lived, purpose-bound Data Protection grant containing the server-derived operator subject and exact target/batch/Repository selection; the raw request cannot set the subject in that grant. This is a new setup authorization seam using existing Identity, not a new login or the Story 18.1 source grant.

October Web verifies the grant locally; the headless generator presents it to the Web authorization endpoint. That endpoint validates protection, expiry and scope and rechecks current Identity role, Repository visibility and deployment target allowlist. It returns a sanitized decision and canonical target identity, never credentials. Both hosts resolve the target ID to a connection only through their trusted local allowlists, confirm canonical descriptors agree, and perform a read-only connected-database identity check before migration. The generator does not reuse Web's request-scoped `IUserContext`, accept a CLI user ID as proof, or treat a successful database connection as authorization. Missing/forged/expired/substituted grants or an unreachable authority fail closed.

The shared policy consumes that trusted authorization result, verifies exact target/batch/Repository agreement and context origins, preserves value/scope/origin/conflict, and commits all setup-owned records atomically within the October database. Ordinary authority and batch data have no cross-database foreign key or distributed transaction, so protected use repeats grant/current Identity, Repository and target checks. It returns the exact target/batch identity and a sanitized outcome. Failed validation, cancellation or persistence leaves no selectable partial batch. An uncertain acknowledgement is resolved by exact target/batch lookup and immutable-input comparison, never by a new target or blind duplicate write.

## Process startup selection

The generator and explicitly enabled October Web each require the same protected activation grant, exact allowlisted target ID and batch ID. Each validates authorization and its local canonical target mapping before opening the October connection or running October migrations. The selector then binds one fixed connection/factory to that database, verifies the batch exists there and that its setup identity matches, and makes only that selection available to October consumers. No latest/previous-batch query, other-database probe, dynamic EF schema, per-request selection or legacy-wiki fallback is permitted. Switching either element requires process restart and fresh authorization.

October Web keeps ordinary Identity/domain database configuration separate from the selected October database. Ordinary Web startup has no October context registration, model configuration or migration path; its authenticated issuance port can use existing Identity without opening an October target. October migration execution is conditional on explicit mode, valid operator grant and allowlisted target authorization; neither host may mutate an unrelated database. Protected setup and later October use repeat live authorization, including after an operator role, Repository membership or target allowlist change.

## Outcomes and failure classes

Report only sanitized target/batch identifiers and one of: missing selection, forged/expired/substituted grant, authorization service unavailable, unauthorized/unlisted target/operator, invalid organizational/context selection, batch absent/mismatch, incomplete provider binding, protected-secret compatibility, migration/storage failure, cancelled, or selected. Logs must omit grants, connection credentials, provider keys, raw source, hidden reasoning and physical source paths. `selected` does not mean contained file tools, native CodeGraph, paid provider inference or Knowledge publication are ready.

## Story 18.1 dependency

The final source association, ID cardinality, grant lifetime, access checks and failure mapping must be replaced with the accepted 18.1 Repository/root/source identity and contained read-only tool contracts after their verified integration. Until that reconciliation, this contract is complete only for independent setup/database/context selection and cannot authorize downstream source reads or task generation.
