# Research: Owned October Batch Setup

All decisions below are static planning conclusions. No database, provider, host or Story 18.1 runtime was exercised.

## Database and context ownership

**Decision**: Use one explicitly owned PostgreSQL database per batch and one dedicated October EF context with fixed `october` schema, `october.__OctoberMigrationsHistory` history table and its own migration folder/model snapshot. The generator and October Web bind an exact database and batch ID at startup. Ordinary Web retains its normal database/Identity/domain contexts. **Rationale**: O-FR17 and O-AR03 in `docs/bmad/planning-artifacts/october-release-epics.md`; the accepted October proposal's “Isolate October behavior” section selects database-per-batch, not schema-per-batch. `VulgataDbContext.OnModelCreating` sets `vulgata` and scans all configurations in its assembly; `Program.cs` registers and migrates Identity and Vulgata contexts unconditionally. **Alternatives**: schema search path or legacy table reuse would not redirect schema-qualified mappings and would risk ordinary model/migration contamination. An extra assembly is unnecessary if configuration discovery is explicitly filtered and verified.

**Decision**: Treat authorized database provisioning as an operator prerequisite, not a setup-side `CREATE DATABASE` action. A deployment-operator-owned allowlist maps opaque target IDs to exact database connection descriptors in each host; both hosts must agree on canonical target identity. The Web authorization service approves an allowlisted target before either host opens it for October migration/setup. Reachability is never ownership proof. The setup writer creates only its own batch metadata in that target, transactionally; exact target/batch lookup precedes any consumer data access. **Rationale**: Story 18.4 acceptance and `docs/agents/testing.md` require owned resources and reject cross-target fallback. **Alternatives**: request-supplied connection strings, “latest” selection, dynamic switching and partially published setup are excluded by O-FR17.

## Identity, organization and context

**Decision**: Persist a server-derived real operator subject and a validated organizational selection. The ordinary Web host authenticates the operator through existing Identity and checks live `ManagementAccess`; its `UserManager`-backed handler proves Administrator/SystemOwner role. It issues a short-lived, purpose-bound protected activation grant scoped to operator, target, batch and Repositories. October Web verifies it locally; the generator presents it to Web's authorization endpoint for protection/expiry and live Identity/Repository/target checks before migration/setup and at protected use. This uses Web's existing Identity owner; request-scoped `IUserContext` cannot be the headless generator's identity source. For a System member, require current owner-filter visibility and matching membership. For a standalone Repository, require current `ManagementAccess` plus an existing `SystemId == null` Repository; do not pretend it has a System owner. The current `RepositoryAuthorizationVerifier` rejects standalone Repositories and cannot be reused unchanged. The batch database has no cross-database foreign key or atomic transaction with the authority; a stored subject is provenance, not continuing permission. **Rationale**: PRD FR-1.4/FR-2.1–2.4, canonical glossary, O-FR18, `UserContext`, `ManagementAccessRequirement`, `RepositoryManagementCoordinator` and Story 18.4. **Alternative**: accepting a CLI/request user ID, copying role claims or fake Identity rows, or treating a reachable DB as owned would make authority forgeable or stale.

**Decision**: Retain selected Global, optional System, and Repository advisory context as separate values with scope, originating record and selection time, plus explicit disagreement indicators; do not collapse them into one source-qualified statement. **Rationale**: PRD FR-7.3, Story 18.4/O-FR02 and AD-2. Current `GlobalContext`, `System.Context`, `Repository.Context` provide candidate values, while `IContextCompositionService.ComposeEffectiveContextAsync` returns flattened text and cannot alone retain origins. **Alternative**: reuse flattened text only would lose provenance and silent conflicts.

## Provider and secret configuration

**Decision**: The provisional implementation route is an explicitly supplied host configuration source per process with complete endpoint/model/credential reference/API type and separate Worker/Chat role profiles. The operator must supply the source and precedence; no `.env` path is inferred or discovered. A shared profile requires an explicit declaration. **Rationale**: O-FR19, PRD FR-3.1–3.4, accepted October proposal's provider section and existing `Program.cs` Data Protection/registrations. **Alternatives**: silent field mixing/auto failover is prohibited. A database configuration route may be substituted only after explicit selection and design reconciliation; encrypted-row copy then requires compatible Data Protection keys, application identity and purpose (`SecretEncryptionService` uses a purpose-specific protector).

**Decision**: Binding checks configuration completeness, not paid provider availability or model quality. Sanitize source identity and failure class in diagnostics; never emit credentials, raw source or a false tool/Knowledge readiness claim. **Rationale**: Constitution V, AD-32 and Story 18.4. **Alternative**: live inference as a setup health check would spend resources and conflate later qualification.

## Source integration pending Story 18.1

**Decision**: Leave the prepared-source binding interface/columns/grant adaptation unspecified until an integrated, verified 18.1 baseline is present in this checkout. The batch can carry an internal unready dependency state; it cannot be claimed fully usable for source analysis until reconciled. **Rationale**: Story 18.1 owns Repository/root/source identity and contained read-only tools; Story 18.4 depends on it. The current generic Git-bound Source Snapshot is a distinct contract, as the glossary and October proposal explain. **Alternatives**: deriving a fake revision, copying physical paths, or designing a second tool grant would duplicate or contradict 18.1.

## Compatibility and verification

**Decision**: Add conditional October composition and migration only when explicitly enabled; preserve normal Web's existing migration/role seeding path. Test the normal EF model/migration list and startup behavior against the current boundary, then test two owned PostgreSQL databases with identical October schema. **Rationale**: O-AR01–04, `Program.cs`, `VulgataDbContext.OnModelCreating`, constitution IV and testing guide. **Alternatives**: SQLite-only or static schema inspection cannot prove PostgreSQL cross-database behavior. Neither controlled tests nor a migration script alone proves Docker/provider/source-tool qualification.
